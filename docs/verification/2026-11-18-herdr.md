# Herdr Core surface verification, 2026-11-18

## Scope

The new surface targets a running local Herdr Core on macOS. The reference host
uses hc 0.1.21. Linux continues to use tmux; the Herdr adapter is not available on
Windows. A platform CI result does not establish live provider behavior there.

Herdr Core is the terminal owner. Bridge retains its existing provider-owned
completion and follow-up mechanisms. Herdr's OSC status is not result, delivery
or close authority. Existing terminals outside this task are not control targets.

## Source and installed contract

- Herdr source: `herdrdev/herdr-core` at
  `c7517808d64f06609e4ecf0db1757005373cc3a3`, especially `paths.rs`, `rpc.rs`, and
  `client.rs`. The installed `hc schema` and a read-only Unix-socket `hello`
  returned generation 1 and hc 0.1.21.
- `core.id` is a permanent random core identifier. An address belongs to that
  core, not to the name or position of a terminal window. Process identity still
  needs a separate binding; a core identifier does not prove that a process is
  alive or that a terminal has not been kept and replaced.
- A terminal opened by hc exported `HC_TERMINAL_ID` and `TERM_PROGRAM=ghostty`.
  This explains why the previous detector selected Ghostty. That probe was
  waited, read and removed after exit.
- The hc core retains the environment of its startup process. Provider caller
  markers therefore need removal in the child launch host even when the Bridge
  caller itself has no such marker. The adapter must not restart the user's core
  to change that environment.
- The official Codex `rust-v0.169.0` source and installed 0.169.1 CLI document
  `--no-daemon` as running without the shared
  background daemon even when one is already running. The Herdr launch floor is
  conservative: stable 0.169.0 or newer. Other terminal surfaces do not acquire
  this option or version gate. The source is
  [Codex TUI CLI at rust-v0.169.0](https://github.com/openai/codex/blob/rust-v0.169.0/codex-rs/tui/src/cli.rs);
  this source check establishes option availability, not execution of 0.169.0.

## Regression evidence

Both comparisons used the pre-fix implementation in the existing clean baseline
at `328d8f1`, with the new test present and the corresponding production fix
absent. Neither comparison reset unrelated work.

- `herdr_host_selection_precedes_its_ghostty_terminal_identity` failed with
  selected kind `ghostty` instead of `herdr`. The child process supplies the
  environment, and the test performs no terminal launch or socket request.
- `herdr_codex_launch_keeps_tools_in_the_terminal_process` failed because the
  complete launch plan contained zero `--no-daemon` options instead of one.
  This is a launch-plan fixture, not a real Codex process.

Review of the first implementation found three reachable failure paths. Five
additional deterministic tests failed before their fixes and all 29 Herdr adapter
tests passed afterward:

- A server error after creation (`internal` or `unavailable` from registry
  persistence) must reconcile the created terminal instead of assuming nothing
  was created. Upstream `api/run.rs` calls `flush_saved()` after `start()`.
- A later close or failed-launch cleanup observation can show a changed program
  or `keep` setting. Every observation must still match before acting.
- Upstream `terminal.list` also queries configured remote machines. Recovery now
  uses the launch's random local name with `terminal.get`, then checks its local
  address, launch label and argv. It never lists or queries remote machines.

The core has no conditional kill/remove API. Checks do not make a separate read
and action atomic against concurrent changes by another client of the same user.

## Candidate runtime

The candidate after these review fixes passed all five self-test steps for each
provider: ask, initial result, tell, follow-up result and explicit close.

| Provider | Version | Result |
| --- | --- | --- |
| Codex | 0.169.1 | 5/5 |
| Claude Code | 2.1.327, `opus` | 5/5 |
| Agy | 1.5.10 | 5/5 |
| Pi | 1.5.0 | 5/5 |

These were authenticated CLI runs in a task-owned hc 0.1.21 core with separate
socket, state and config directories. The core was started with dummy Claude
caller markers to exercise the existing launch host's environment cleanup.
No user core was restarted. Self-test's `isolated` field is false because the
test harness did not choose its own state root; the caller supplied the separate
task state root explicitly.

A separate Claude self-test launched from an hc terminal, without `--terminal`,
selected Herdr and passed 5/5. Its helper terminal exited with code 0 and was
removed. Explicit terminal selection and stale caller rejection are also covered
by the deterministic tests.

A Codex verification turn executed a Python command through its actual execution
tool. The command printed the child terminal's `HC_TERMINAL_ID` (`t12`) and
`TERM_PROGRAM=ghostty`; the addressed result and the recorded tool call/output
agreed. This checks that `--no-daemon` keeps tools inside the created hc terminal,
in addition to the native queue follow-up exercised by self-test. The session was
closed afterward.

A further Codex self-test passed 5/5 while the existing shared app-server daemon
was running. `codex app-server daemon version` reported `status=running`, with
both CLI and app server at 0.169.1. The daemon was not started, stopped or changed
for the test. This specifically checks native queue follow-up beside an existing
daemon, the configuration questioned during Claude's review.

The initial development build also passed 20/20 with Codex 0.169.1, Claude 2.1.327,
Agy 1.5.9 and Pi 1.5.0, and returned the visible Claude screen through `screen`.
After that initial matrix, the isolated core held no terminals and all eight
recorded provider/wrapper PIDs were absent. The later candidate matrix above is
the result after the lifecycle fixes; the initial matrix alone was not release
acceptance.

These runs verify the local hc terminal API and real provider processes. They do
not establish Herdr GUI rendering, remote control, or live provider behavior on
Windows or Linux.

## Local automated checks

2,008 tests with six ignored tests. Ignored live tests are not runtime evidence.
Clippy (`--all-targets -- -D warnings`), formatting, language, agent-instruction,
integration-generation consistency and `git diff --check` all passed. Python
unittest discovery ran 120 tests with two skipped (118 executed successfully).
Claude also checked Clippy for Linux and Windows targets; those checks establish
compilation only. Platform runtime tests belong to their CI runners.
