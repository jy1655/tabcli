## Close after the program ended outside TAB

On macOS, `ask codex --detach` launched `session-4puSp7` on Herdr, and a following `result`
returned `READY`. The terminal's program was then ended with `hc kill`, outside TAB. The core
reported the terminal as finished, and `inspect` reported the owner process as not alive with
the stored state still `ready`. `tabcli close-session session-4puSp7 --explicit` returned
`closed: true`; the core no longer listed the terminal, and its terminal list matched the
list from before the launch. A second explicit close also returned `closed: true`, and
`inspect` then reported the state `closed` with no residual surface.

## Failed attempt: Herdr from an elevated SSH session

One Windows attempt did not pass. `self-test pi --terminal herdr`, run from an SSH session
that was elevated on this host, timed out in `ask` after 31.722 seconds with
`provider launch timed out before startup was confirmed`. The three following steps were not
run, cleanup passed and no terminal remained (`session-mDH1E8`). The launch log held the
cause:

```text
herdr_host_refused: Herdr launch directory is not private to the current user: session directory owner differs from current user
```

The session directory created by the elevated caller was owned by the Administrators group,
while the core and its launch host ran without elevation in the desktop session, where a new
directory is owned by the user. This is the private-directory rule in
[the terminal guide](../terminals.md#herdr-core-on-native-windows).

The published 0.4.48 executable, from the release archive after its checksum matched
(SHA-256 `340cb1cc8e0eb01899a06bb298806fe8b08a2fe753dd4db465e4a25a2de8b382`), was run the
same way. It wrote the same log line, timed out in `ask` after 31.836 seconds, skipped the
same three steps and passed cleanup (`session-ekmtWR`). The result is therefore not specific
to this candidate. In both builds this refusal is written to the launch log only, and the
caller waits for the launch deadline.
