# Agent Bridge 0.1.2: macOS verification

## Scope and source

0.1.2 contains two refactors and no behaviour change: session records behind
`session::Reader` and `session::Store` with the turn, close and repair
lifecycle (PR #73), and surface ownership and close authority behind the
terminal seam (PR #74). This record covers what was run on macOS for the
0.1.2 candidate. It is not evidence for native Windows or Linux runtime
behaviour.

The tested implementation is commit
`216e176fd461327ec48e29b2662538a349d51d2c`: the last source commit
`02310af69cd02aed1bea28bcf0cb2c3e75b0998a` plus the version bump. Later
changes in the release branch add this record, the release notes and README
text only. The release binary (`cargo build --release --locked`) reports
`agent-bridge 0.1.2` and has SHA-256
`9165e0ea8800ce39c8cbbc2fb10aa2d76de95007832475492dee2e25697d8e21`.

Environment: Apple Silicon, macOS 26.6.2 (25G83), Rust 1.98.1,
Codex CLI 0.160.1, Claude Code 2.1.291. The commands ran from a shell inside
WezTerm.

## Review

Rounds 3a, 3b and 3c of PR #74 were each implemented in a fresh Codex session
and compared function by function with their parent commit in a separate Codex
session; the whole branch was reviewed once more before the pull request. Every
verdict was `MERGEABLE AS IS`. The reviews found the moved bodies, comments,
error texts, serde attributes and `#[cfg]` gates identical apart from
visibility, path qualification and rustfmt signature wrapping. A review of the
source is not a runtime check.

## A session of 0.1.1 continued by 0.1.2

The installed 0.1.1 launched `session-UCOeFF` (Codex, WezTerm) in the ordinary
state root and completed its first request. The 0.1.2 candidate then ran
`inspect` (owner alive, identity verified, one event), `tell` (completed with
the expected answer, two events) and `close-session --explicit` (closed). The
wrapper process inside that session was the 0.1.1 binary throughout.

## First attempts that timed out

Before the version bump, the release build of
`f10d85f0aece88cbb97149a97614afd9d748f2b4` (SHA-256
`1b28a7f2673e43d46ec82faa6036b7f6bc56ab6ec4ac7bc141ae9bee84f384af`, reporting
0.1.1) was tested the same way. It differs from `02310af` only in the
visibility of six macOS process-table items.

| Terminal | First attempt | Next attempt |
| --- | --- | --- |
| WezTerm | Passed (`session-wvC7mI`, 14.763 s) | not repeated |
| Terminal.app | `ask` timed out after 28.2 s: `Terminal.app automation timed out` (`session-nNBduV`) | Passed (`session-BcDwlj`, 16.138 s) |
| iTerm2 | `ask` timed out after 28.2 s: `iTerm2 automation timed out` (`session-2vFuXz`) | Passed (`session-QVQMVS`, 15.553 s) |
| Ghostty | `ask` timed out after 28.2 s: `Ghostty automation timed out` (`session-bP0JAF`) | Passed (`session-tABKU2`, 19.272 s) |

What is known about the three timeouts:

- Each ended while the surface was being created, before a surface handle
  existed and before any ownership or close-authority code runs. Cleanup of
  each session passed and nothing was resent.
- Terminal.app was not running before the first attempt. The installed 0.1.1
  then timed out in Terminal.app in the same step (`session-RJjoL9`), and a
  plain `osascript` window count to Terminal failed with AppleEvent timeout
  `-1712` at that moment, while the same probe to iTerm2 and Ghostty answered.
  A few minutes later the Terminal probe answered and all attempts passed.
- The cause was not established. A macOS Automation consent prompt answered in
  the meantime and a slow first launch of Terminal.app are both consistent
  with what was observed; neither was confirmed. The timeouts are not counted
  as passes, and they are not evidence about the refactor in either direction.
- Terminal.app afterwards listed three hidden windows that no Bridge handle
  owns: a login shell, a window with an ended tab, and the lingering object of
  a closed test window (the behaviour of #64). They were left as found.

## Not exercised

- Warp (no reachable Control endpoint was looked for), Agy and Pi.
- A close after the owner died, an interrupted close, and the Terminal.app
  paths for a restarted or second Terminal process. Unit tests cover them; no
  live run did.
- Native Windows and Linux at runtime.
- The providers' default approval mode: every round trip here used `--yolo`.
