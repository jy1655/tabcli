# Agent Bridge 0.1.1: macOS verification

## Scope and source

The Windows work in PR #71 removes the shared Codex daemon prerequisite from
the common provider adapter. Both macOS and Windows use that same sender and
completion correlation. No additional macOS transport or provider fallback was
needed. The README's older doctor section was corrected: the daemon observation
is advisory, not a queue delivery gate.

The tested implementation is commit
`64e5c484d8252194c5134e8ba744ebee40ea6eff`. Subsequent macOS changes in this PR
only correct documentation and record this verification. The local debug binary
reports `agent-bridge 0.1.1` and has SHA-256
`11e1eac0eb4cdab29e1eeb4af6ca8149037d521be7d9e52d292a6bfb9f6ba256`.

Environment: Apple Silicon, macOS 26.6.2 (25G83), Rust 1.98.1,
Codex CLI 0.160.0, Claude Code 2.1.288, Agy 1.2.16, Pi 1.0.0.

## Authenticated terminal round trips

Tests used the public `self-test` command, the existing trusted agent-bridge
workspace, `--isolated --json`, and no model, effort, or bypass override.
Each passing row verified `ask`, the first exact marker result, `tell`, a
separate follow-up event with the exact marker result, and owned-session cleanup.
Each pair of Codex events named the same provider thread and different turn IDs.
All test sessions ended in `closed`; their records were retained.

The optimized 0.1.1 release binary also passed the complete Codex/WezTerm
round trip in 24.893 s (`session-iOsEuk`). `inspect --timeline`, `result --list`,
and `doctor --probe` succeeded with that binary. A before/after content-hash
comparison verified that these queries changed no stored session record;
the daemon diagnostic explicitly said that a shared daemon is not required.

Pi's first model call returned `Encountered invalidated oauth token for user,
failing request`. Bridge published the failure and closed its session without
resending. This is failure-reporting and cleanup evidence, not a Pi round-trip
pass. Pi 1.0.0 also failed to start under the invoking shell's Node 20.9.0 because
`node:module` lacked `enableCompileCache`. The test explicitly put the already
installed Node 22.23.2 after the installed Pi command's directory on `PATH`;
it then reached the provider authentication failure. No shell startup files or
provider credentials were changed.

## Permissions and remaining limits

The first Terminal.app and iTerm2 launches timed out in Automation before the
provider started (`session-9zsSgV`, `session-28PAO6`). The user confirmed that a
Terminal control approval prompt was displayed and approved the visible control
requests. Terminal.app then passed. An iTerm2 retry (`session-Bsr9q8`) still
timed out; this run does not establish an iTerm2 round trip. Both failed launches
were reported as failures and their Bridge session cleanup passed.

Computer Use explicitly refused access to Terminal.app and iTerm2. No alternate
screen-control route was used to bypass that restriction. The tests above use
the product's public CLI. Cleanup is verified by the Bridge lifecycle and native
adapter checks; this run does not claim physical keyboard behavior, independent
visual disappearance, or preservation of every foreground selection.

The user's shared Codex daemon was already running and was left unchanged.
These authenticated Mac tests therefore do not establish a daemon-absent TUI
round trip. That path is covered here by the Unix adapter regression; the
[Windows native CLI protocol probe](2026-10-04-codex-queue.md) separately proves
cross-process delivery without a daemon using a mock model. Queue acceptance,
model completion, and MCP authentication remain separate observations.

Warp's official instance-list command returned `instances: []`; no reachable
Control endpoint was observed, and no Warp round trip was claimed. Agent-picker
switching (#57), manual additional TUI input (#65), and new MCP authentication
verification (#56) were outside this check.
