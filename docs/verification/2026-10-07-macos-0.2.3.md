# Terminal Agent Bridge 0.2.3: macOS verification

## Scope and source

0.2.3 keeps the record of a Warp launch that fails after its tab exists (#87), reports whether
Pi has credentials configured for a session's provider in `doctor` and in a timed-out
self-test (#83), and documents the Codex startup line about the shared background server
(#89). This record covers what was run on macOS for the 0.2.3 candidate. It is not evidence
for native Windows or Linux runtime behaviour.

The tested source is commit `7dfa9042be5ecb82010abae29ddef85df556c720`, the version bump. Later
commits on the release branch add this record, the release notes and the README lines that
point to them. The release binary (`cargo build --release --locked`) reports `tabcli 0.2.3` and
has SHA-256 `1453ecb9cefea6269e7f45912246ab17f075356a55935955a386c66cea2874da`. It is a local
build with Rust 1.97.1, the version the Release workflow pins.

Environment: Apple Silicon, macOS 26.5.2 (25F84), Codex CLI 0.160.1, Claude Code 2.1.292,
Agy 1.3.0, Pi 1.0.0. The commands ran from a shell inside Ghostty; the screen was unlocked
throughout (checked before and after the runs with
`ioreg -n Root -d1 | grep CGSSessionScreenIsLocked`). A shared Codex app-server daemon
(0.160.1) was running on the machine during the runs; managed Codex sessions run on their
embedded server regardless (#89).

## The Warp fix (#87)

Fake-runner tests in the Warp adapter cover the control-binding write failure with a confirmed
cleanup (no handle, plain failure) and with an unconfirmed cleanup (handle retained in
`terminal.json`, session `failed`, residual-surface warning), the close refused while the surface
is being created, and the late handoff into an already closed session whose warning survives a
repeated close. The implementer ran the three new tests against the unchanged adapter first:
0 passed, 3 failed. No Warp session was launched for this release; Warp support is not
live-verified (#63), and the record write that fails here has not failed live. The recovery
close of a retained Warp tab is not implemented (#87 stays open).

## The Pi credential check (#83)

Unit tests cover the parsing of each `pi auth check --no-refresh --json` shape sampled from
Pi 1.0.0 on this machine (status fields only; no credential was printed or stored):

| Command | Output | Exit |
| --- | --- | --- |
| `--provider openai-codex` | `{"status":"ready","provider":"openai-codex","authType":"oauth"}` | 0 |
| `--provider anthropic` | `{"status":"ready","provider":"anthropic","authType":"oauth"}` | 0 |
| `--provider openai` | `{"status":"not_ready","provider":"openai","reason":"credentials_not_configured"}` | 1 |
| `--provider bridge-unknown-provider` | `{"status":"not_ready","provider":"bridge-unknown-provider","reason":"provider_not_found"}` | 1 |
| `--model bridge-unknown-provider/model` | `{"status":"invalid","provider":"bridge-unknown-provider/model","reason":"invalid_state"}` | 2 |

Further tests cover a missing command, a timeout, malformed output, `ready` with an unlisted
`authType` (kept as evidence; Pi's `auth-check.js` derives the exit code from `status` alone),
the provider derivation from a qualified model id, the doctor field for a session and for
`doctor --provider pi`, and the self-test reason enrichment on both result timeouts. Live rows
are below.

### Pi without credentials (#83)

- `session-47qlRW`: `ask` passed in 2.1 s (Pi reported startup and the request was accepted),
  `initial_result` timed out after 120.0 s with the reason
  `waiting timed out; the request was not cancelled or resent; Pi provider credentials
  not_ready for openai: Pi has no credentials configured for this provider.`; `tell` and the
  follow-up result were not run; cleanup passed in 0.3 s and the session is closed. This is the
  first live record of the enriched reason. No event was recorded for the request, and the
  refusal on Pi's screen was not read: the self-test closes the surface before that.
- `doctor` on an ordinary session: `ask pi --workspace <this repository> --terminal wezterm
  --model openai/gpt-4o-mini --timeout-secs 30` (`session-1zRB0f`,
  `request-1791347706792559000-43462-0`) returned the timeout error after 30 s;
  `doctor session-1zRB0f --probe --json` reported the check `pi_provider_credentials` with
  availability `unavailable`, reason code `pi_provider_credentials_not_ready` and evidence
  `{"status":"not_ready","provider":"openai","authType":null,"exit_code":1}`;
  `close-session session-1zRB0f --explicit` closed it. Nothing was resent.
- The `ready` form was observed only through the passed Pi row above, whose provider
  `openai-codex` is logged in on this machine; `doctor --probe` was not run on that session.
