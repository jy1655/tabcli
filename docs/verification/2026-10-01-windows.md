`fix/codex-follow-up-target-20261001`, the 0.0.9 candidate with the macOS work of

## Defects found on native Windows

### 0.0.8 could not open a session

The console launch passes its command to PowerShell as one double-quoted
`-Command` argument and refuses a command that contains a double quote. 0.0.8
added a line to the bootstrap command that writes the wrapper exit code to
`launch.log`, and wrote it with a double-quoted PowerShell string. Effect: every
`ask` on native Windows failed before a console existed. Checked with the
published `agent-bridge-0.0.8-x86_64-pc-windows-msvc.zip` (checksum verified):
`ask` failed after 0.2 seconds with the error in the block below:

```text
failed to open Windows Console surface for session session-KDOjBL: Windows console launch command contains an unsupported double quote
```

0.0.7 does not have that line and is not affected. The candidate had the same
defect. Fix: the string is single-quoted. A new Windows test builds the
bootstrap, runs it through the launch's own command line with a stub that exits
with 7, and checks both the exit code and the `wrapper_exit_code=7` line in the
log. The test failed before the fix.

### A record could not be replaced while it was being read

Bridge replaces its JSON records by renaming a temporary file over them. Windows
refuses that rename while any other handle to the target is open. The launcher
polls `launch.json` and `status.json` while the wrapper replaces them. In one
live run the replacement of `launch.json` failed with access denied and the launch
failed (`session-F5q8vy`).

Fix: the rename is repeated for at most one second when it fails with access
denied or a sharing violation. Every other error, and a target that stays open for
the whole second, is still an error. On other platforms nothing changed. Proof:
two Windows tests. One holds the record open for a moment and expects the
replacement to succeed; it failed before the fix. The other keeps it open and
expects the failure after the bounded wait.

### A screen with full-width characters could not be read

`native-console-control screen` reads the console row by row. The console returns
a full-width character once although it fills two cells, so a row with Korean text
or an emoji holds fewer characters than cells. The helper treated a short row as
a failed read: `could not read the entire managed console screen`. The guarded
trust-dialog response reads the screen, so shared consent could not answer a
dialog whose screen showed a Hangul path.

Fix: a row is accepted with the number of characters the console reports; only a
count beyond the row is an error. A unit test covers it, and the Agy dialog for
the workspace `ab-consent-한글` was read and answered live.

### The trust store check on Windows looked at the owner alone

This defect was not found on the test PC but by the CI of the release pull
request, #59. It was the first time the consent code ran on a Windows runner.
On commit `878511e` nine tests of workspace consent and provider trust failed in
the Windows job with `trust store owner differs from current user`. They pass on
the test PC. The reader of a trust store required the store's owner to be the
user's own account. The job on the runner is an elevated process, and Windows
makes the Administrators group the owner of the files that an elevated process
creates. The test PC runs without elevation, so its files are owned by the
user. Outside CI, for a user who works in an elevated terminal, shared consent
finds no trust, and the Agy initial paste is withheld because its trust
evidence cannot be read.

In the first repair, commit `a6c2c94`, the owner is accepted when it is the user
or the default owner of the process, which is the owner that the process's own
new files get. A review of that commit (round 7 below) found that the owner does
not say who can change a file. A trust store owned by the Administrators group,
in a shared folder, with an access rule that lets a standard user modify it,
would be accepted by an elevated Bridge whose store path points there through
`CODEX_HOME`, `CLAUDE_CONFIG_DIR` or `PI_CODING_AGENT_DIR`. The missing check
was older than the repair: a store owned by the user with such an access rule
was accepted before as well. On macOS and Linux the reader has refused a
group-writable or world-writable store from the start.

In the second repair, commit `7a27bfb`, the reader takes the owner and the
access list from the same open file that it reads the content from. It refuses
a store without an access list. It refuses a store with an access rule that lets
an account other than the accepted owners, the system, the Administrators group
or `OWNER RIGHTS` write data, append data, change the access list or change the
owner. It refuses a store with an access rule that is neither a plain allow
rule nor a plain deny rule, such as a conditional rule. Deny rules and rules
that apply only to inheritance are ignored. Read access for other accounts stays
allowed.

The stores in the user profile (`~/.codex/config.toml`, `~/.claude.json`,
`~/.gemini/antigravity-cli/settings.json`) carry access rules for the system, the
Administrators group and the user, all with full control. The Codex and the Agy
store also carry a read-only rule for a local group, `CodexSandboxUsers`. All
three pass the check. The temporary directory lets `CodexSandboxUsers` and one
account that could not be resolved modify its files. A file created there with
a plain write is refused. The fixture of one Codex adapter test was such a file.
The test failed on the test PC only, and the fixture is now created the way
Bridge creates a private record.

Windows tests set real access lists on a test file. Refused: write access for
Everyone; the right to change the access list for Authenticated Users;
append-only access and the right to change the owner for an account that does
not exist; no access list; a conditional rule. Accepted: read access for
Everyone; full control for the system and the Administrators group; a deny
rule. A test of the decision covers the owners, including a store that an
elevated process wrote and that is read without elevation, which stays refused.
The Windows CI job passed on `a6c2c94` and on `7a27bfb`. Live on the test PC
with the repaired build: `session-qd4OuM` read the Codex store (consent
`verified`, `applied=codex-config-override`), and `session-qck41j` read the Agy
store (consent `verified`, initial paste delivered, `ask` in 15 s).

The check describes who can change the store at the time it is read. It cannot
tell who wrote the content earlier, so a store that another account could change
before has to be created again. A profile whose files carry a write rule for
another account, for example in a domain setup, is refused. That was not tested.

## What Windows Terminal allows

These facts were measured on this host with probe scripts that sample the
foreground window every 5 to 10 ms:

| Subject | Result |
| --- | --- |
| A console created with `CREATE_NEW_CONSOLE` while Windows Terminal is the default terminal | Opens in a new Windows Terminal window. With a Windows Terminal window in front, the new window took the foreground 59 to 69 ms after the process was created, also when the process asked to be shown without activation |
| `wt.exe -w <name> new-tab` | Creates the window with that name when it does not exist, and adds a tab to it when it does |
| A window that `wt.exe` creates when it is started with `SW_SHOWNOACTIVATE` | Is not activated while another application is in front. It is activated when a Windows Terminal window is in front |
| A command line dispatched to an existing window | The window comes to the front 33 to 40 ms later |
| A new tab | Is always selected. No option creates a tab unselected, and no command selects the earlier tab again |
| The environment of the `wt.exe` invocation | Is passed to the process of the tab |
| `%NAME%` and `;` in the command line | Windows Terminal expands the first and splits the command at the second |
| A tab whose process ends with a failure code | Stays open with a message; a tab whose process ends with code 0 closes |
| The console window of a tab | A hidden window. Its root owner is the Windows Terminal window that hosts the tab |
| The console window of a console that was handed to Windows Terminal | Belongs to Windows Terminal's console host process, not to the first process of the console |

## The change

### A tab first, a window only when no tab can be had

A managed console is opened with the command in the block below. Windows
Terminal creates the window named `agent-bridge` when it does not exist and adds
a tab when it does.

```text
wt.exe -w agent-bridge new-tab <agent-bridge.exe> native-console-host <session directory>
```

`wt.exe` creates the tab's process itself, so the launcher cannot create the
root suspended and attest it as it does for a console window. The tab therefore
runs the internal command `native-console-host`, the tab host. The tab host
creates the same PowerShell root, with the same command line and environment as
before, suspended, in the tab's console, and writes its attested identity
(creation time and executable path) to the private session directory. The
launcher binds the surface (`terminal.json`) and only then accepts the offer.
The tab host then starts the root. The root is created inside a job that ends it
when the tab host ends, and the job is released only after the root was started.
A tab host that dies before that leaves no process.

Whether the root is started is decided exactly once: the tab host, to start it,
or the launcher, to give the tab up, creates one file with create-new semantics,
and the other side finds it there. A launcher that gives up first ends the
suspended root. A launcher that finds the tab host's decision ends nothing: the
surface counts as started and stays bound, and the launch goes on to wait for the
provider like every launch. If the provider never starts, the launch fails
there, a wrapper that starts later is not allowed to start a provider, and
`close-session` ends what is left.

The tab host leaves the tab's console once the root has attached to it, and
confirms the start only then. It waits for the root and exits with code 0, so the
tab closes when the session is closed. The tab host records its own process id
and identity in the session directory before it offers a root; a tab host that
cannot write that record refuses, and a console window is used. A close reads the
record: a tab host that it still finds in the console is ended last and without a
failure code, and a tab host that is still alive one second after the root has
ended is taken as stalled and ended the same way, so that no tab outlives its
session. A close that finds the record but cannot read it ends nothing and
reports that. A root that was never started has reached no console, so a close
cannot attach to it. The close ends such a root on its own only when the session's
records show that the wrapper never ran.

A console window is created instead of a tab when `wt.exe` is not on an absolute
`PATH` entry, when the desktop has no shell window, when the path of Windows
Terminal, of Agent Bridge or of the session directory contains a character that
Windows Terminal would change (`;`, `%`, a double quote, a control character, a
leading `-`, a trailing backslash), when no tab host offers a root within 8
seconds, or when the tab host refuses. The request for the tab is withdrawn
first. `launch.log` records the surface and, for the console window, the reason.
Every control path after the start (`tell`, the screen read, the guarded dialog
response, `close-session`) is the same for both surfaces: it addresses the root
by its recorded identity.

### The window of the tab is a setting

By default the tab goes to the dedicated window and never to a window the user
works in, because a new tab is always selected and the earlier tab cannot be
selected again: a tab in the user's window takes the keyboard inside that window.
A user who prefers the tab in the window they use can say so with the command in
the block below. `current` uses the most recently used Windows Terminal window;
`dedicated` restores the default; without arguments the command shows the
settings.

```text
agent-bridge settings [windows-tab-window <dedicated|current>] [--json]
```

The setting is one private record, `settings.json`, in the state root. A record
that cannot be read is reported in `launch.log`, and the dedicated window is used.

### The keyboard is given back

`wt.exe` and the console window are started with `SW_SHOWNOACTIVATE`. That is
enough only when Windows Terminal creates a new window while another application
is in front. For every other case the launcher remembers the window that has the
foreground before it creates the surface, and gives the foreground back when the
window that hosts the new surface has taken it. That window is never guessed. A
process inside the console reads it from the console's own window: the tab host
reports it with its offer, before the root is started; for a console window a
control helper, `native-console-control window`, attaches to the started root's
console and reports it. A window the user goes to in the meantime is remembered
instead, and gets the keyboard back from then on. A terminal window that merely
appeared during the launch is not treated as the surface's.

The foreground is watched from before the surface is created until 600 ms after
its start, because a window that was sent back can come to the front once more on
its own; 54 ms after the first time was measured. The surface's window in front
again more than 200 ms after the keyboard was given back is taken as the user's
choice and keeps the keyboard. Earlier than that the launch cannot tell the
user's selection from the window's own activation and gives the keyboard back.
The watching is done by a thread of its own, so that those times are measured
while the launch waits on files and processes. The launch never waits for that
thread longer than 250 ms: giving the foreground back goes through the input
queue of the window that holds it, and a window that has stopped answering can
hold such a call.

The tab host discards the console input that was typed before it starts the
root. A key typed while the new tab had the keyboard therefore does not reach the
session: an Enter would have answered the first dialog the provider shows.
`launch.log` records what became of the foreground, for example the line in the
block below:

```text
foreground=kept; given back 1 time(s); host window 0x630740
```

Everything about the foreground is best effort and never fails a launch.

### Agy needs no reload window on Windows

The macOS work of the same day found that the reload which used to wipe a paste
is Agy's reaction to an approved trust dialog, and replaced the macOS window by
trust evidence. It kept the 45-second window on Windows because Windows had not
been checked again. On Windows, in a workspace that was trusted before the launch,
that reload never came: with the 45-second rule the paste waited for the window to
end and was received 2.1 seconds later; without the window the paste followed the
quiet period and was received 1.2 and 1.4 seconds later. The Windows rule is now
the same as on macOS plus the redraw line that Agy logs only on Windows: the two
trust facts, `CLI startup completed`, `Full redraw completed`, and one quiet
period of 3.5 seconds. The receipt requirement is unchanged. The gate keeps the
code that evaluates a window only for the tests, which replay the recorded
sessions against the former rules.

## Review findings

Six rounds by Codex through Agent Bridge on the uncommitted change changed the
implementation:

- Round 1 (`session-ovXxXw`) found four defects in the first version of the tab
  surface: the launcher's cleanup ended only the root after the tab host had
  started it, which could leave the wrapper and the provider running; a tab host
  that died before its offer left a suspended root that nothing tracked; a close
  that came right after the start could end the tab host with a failure code and
  leave the tab open; and the keyboard guard treated every terminal window that
  appeared during the launch as the surface's.
- Round 2 (`session-65P83Z`) accepted the direction of the fixes and showed that
  three of them still had a gap: the launcher could read "not started" and the
  tab host could start the root before the launcher ended it; the job was
  released before the root was started; the root existed for a moment before it
  was put into the job; and a close could still find the tab host in the console.
  It also found that the guard took the keyboard back when the user selected the
  new session's window after the first give-back. What closed them: the single
  create-new decision between the tab host and the launcher, a root that is
  created inside its job and released only after its start, a close that ends
  the tab host last and with code 0, and the 200 ms limit on answering a window
  that comes to the front again.
- Round 3 (`session-mFJsm1`) found that ending a console during startup with the
  close helper could still leave processes behind: the helper ends the processes
  it saw when it attached, and a root that has just been started starts more. It
  also found that the tab host could not be told when a process snapshot failed,
  that a window the user went to stopped the keyboard guard for good, and that
  a late look could mistake the window's own reactivation for a selection. What
  closed them: the launcher no longer ends a console during startup; the guard
  remembers the window the user went to; the foreground is watched by its own
  thread.
- Round 4 (`session-fLh7dQ`) found that the launch could hang on that thread when
  a call into the window system hung, that a root which the tab host had decided
  to start but never started could not be closed, that a terminal window the user
  went to before the surface was known was not remembered, and that telling the
  tab host by its age fails when the clock is set back. What closed them: the
  launch waits for the watcher for at most 250 ms; a close ends a root that was
  never started; every window the user goes to is remembered; the tab host
  records itself.
- Round 5 (`session-z4VPrk`) found that such a close left a stalled tab host and
  its tab behind, that the record of the tab host was written on a best-effort
  basis, and that the time of a give-back was taken before the call instead of
  after it. What closed them: a close ends a stalled tab host; the record is
  required before a root is offered, and a close that cannot read it ends
  nothing; the time is taken after the call.
- Round 6 (`session-p1crBp`), a short confirmation of round 5, found two more
  cases of the same kind: a root that ends while a close is coming left a stalled
  tab host, and an unreadable leftover record made the fallback session
  impossible to close. Both were fixed and are covered by tests. No review ran
  after that fix.

The live check of an intermediate build found one more defect that no review had
found: the fallback console window kept the keyboard (see the table above).

Two more rounds by Codex through Agent Bridge reviewed the repair of the trust
store check, on the commits:

- Round 7 (`session-aWmQJx`) reviewed `a6c2c94`. It found no defect in how the
  owners are read. It found that accepting the default owner let through a
  store that an unrelated standard user may change, because nothing checked the
  access list. The access-list check of `7a27bfb` closed it.
- Round 8 (`session-qd4OuM`) reviewed `7a27bfb` and the two commits together. It
  confirmed how the access list is read, the rights that count as a change, the
  accounts that may hold them, that the scenario of round 7 is now refused, and
  the repair of the test fixture. It found one case that the check does not
  cover: an account that was allowed to change the store can keep the file open
  for writing after its access rule is removed, and write through that open
  file. This was not changed, for two reasons. First: such an account can put
  its entry into the store before its access rule is removed, and no check at
  the time of reading can tell who wrote the content earlier; the check on
  macOS and Linux has the same limit. Second: refusing a store that someone has
  open for writing means opening it without write sharing, and that makes a
  provider's own write fail while Bridge reads. Bridge reads Agy's store every
  100 ms while Agy saves an approved trust decision. Three test cases that round
  8 suggested were added: append-only access, the right to change the owner, and
  an account that does not exist. No review ran after that.

## Side effects of the live checks

Fifty-two sessions were created by this work in an isolated state directory
and closed explicitly. No session created by anyone else was touched.

`codex app-server daemon start` installed the daemon package under
`~/.codex/packages/app-server-daemon` (427.5 MB) and created
`~/.codex/app-server-control` and `~/.codex/app-server-daemon`. The daemon was
stopped again. One update process that the start had left running was ended by
its process id, which had been read once and verified.

Agy's trust store gained one temporary workspace path through the shared-consent
check. It was removed again after the work. The focus probes opened and closed
Windows Terminal windows of their own. One live check with the `current` setting
opened a tab in the user's own Windows Terminal window and closed it again. The
Rust target `aarch64-apple-darwin` was added to the toolchain for the
cross-target lint.
