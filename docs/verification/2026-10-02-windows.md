# Native Windows verification for 0.0.10 — 2026-10-02

The baseline was main at `7ef5daa`, released as 0.0.9 on 2026-10-02. This record
covers the work that followed on the same day: two Codex defects found right
after the release (#60, #61), the three features of #53, #54 and #55, and the Pi
checks that 0.0.9 left open. The test PC ran Windows 11 Home 10.0.26200, Windows
Terminal 1.24.11911.0, PowerShell 7.5.4, Codex CLI 0.159.3, Claude Code 2.1.287,
Agy 1.2.14, and Pi 0.99.2. All live checks used development builds and isolated
state directories. Times are KST.

## #60 — the Codex paste gate

Three Codex sessions were started in new linked worktrees of the repository to
implement #53, #54 and #55. Each sat at an empty composer and received no
prompt. The `ask` commands waited for their deadline. The paste gate of 0.0.9
waits for an exact project entry of the workspace in Codex's configuration, or
for a consent override. Codex showed no trust dialog in a worktree, so nothing
could be approved and no exact entry was ever written.

What Codex CLI 0.159.3 showed, with the 0.0.9 code:

| Workspace | `--yolo` | Evidence | Codex showed |
| --- | --- | --- | --- |
| A temporary directory that nothing trusts | yes | `session-kkpVsB` | The trust dialog |
| A temporary directory that nothing trusts | no | `session-zIFrA5` | The trust dialog |
| A linked worktree of the repository, which has an exact trusted entry | no | `session-nXZtvt` | No dialog; the composer |
| A plain directory below `d:\dev`, which has a trusted entry | no | `session-bZNfcK` | The trust dialog |

Codex's source at `rust-v0.159.3` was read afterwards. The trust dialog is shown
when the active project has no trust level. The active project is the entry of
the working directory and, without one, the entry of the repository root. An
entry of the working directory wins even when it has no trust level. Codex finds
the repository root by reading `.git` itself. For a linked worktree it checks
the registration of the worktree and resolves to the main repository. It does
not run `git` and ignores `GIT_DIR`. The dialog says that trusting in a
subdirectory applies to the repository root.

The first repair (`a802335`) inferred the missing dialog from `git rev-parse
--git-common-dir` and from Codex's configuration, and used the screen only to
look for the words of the dialog. A Codex review through Agent Bridge
(`session-p4tWkE`) found two defects that had to be repaired: an empty screen
passed the screen check, so a wrong inference could paste an Enter onto "Trust
and continue"; and the inference differed from Codex's rule, for example with
`GIT_DIR` set, in a submodule, in a bare repository, and for an exact entry
without a trust level. It also found that the wait looked at the evidence before
it looked at the session.

The repair in the release (`182aca7`) infers nothing. The gate opens on an exact
entry or a consent override as before, and also when the screen of the managed
console shows the empty composer row `› Ask Codex to do anything`. The
placeholder is a constant in Codex's source, and Codex draws the composer only
when no onboarding screen and no view of the bottom pane is active. The screen
is read once a second. The wait looks at the session first. The Agy trust wait
got the same check of the session (`f992b6e`).

Live with the repaired build:

| --- | --- | --- |
| Linked worktree of the trusted repository | `session-oV3YoW` | `ask` completed in 20.4 s |
| Subdirectory of the trusted repository | `session-3rkG5m` | `ask` completed in 20.5 s |
| Directory that nothing trusts | `session-dfrO8a` | Dialog on screen; `ask` failed as `not_sent` at its 45 s deadline; screen byte-identical before and after; no entry written to Codex's configuration |
| Session closed while `ask` waited | `session-kPdsXT` | `ask` ended 0.5 s after the close with the message that the session is closed |

A user who answers the trust dialog while `ask` waits was not run; a test
replays the screens empty, loading, dialog, composer and expects the gate to open
only at the composer.

## #61 — the Codex task title turn

While #60 was checked, one `ask` with a short prompt returned `{"title":"READY"}`
as its result (`session-pJ1JWw`). The recorded thread was created 48 ms before
the recorded turn, at the time the message was submitted, and not at the start
of the TUI. A temporary build that logged every `notify` payload was run four
times with the same short prompt (`session-2qIKg5`, `session-ZxrJge`,
`session-TRpUCU`, `session-XXfRO8`). The build was not committed.

Every session sent two payloads of the type `agent-turn-complete`:

| | Managed turn | Task title turn |
| --- | --- | --- |
| `thread-id` | The thread created at the start of the TUI | Another thread, created when the message was submitted |
| `input-messages` | One element: the prompt as Bridge sent it, beginning with `[Agent Bridge native delegation]` and ending with the turn marker | One element: `Generate a concise, single-line task title ...`, then `User prompt:` and the whole message, turn marker included |
| `last-assistant-message` | `READY` | `{"title":"READY"}` |
| `client`, `cwd` | `codex-tui`, the workspace | The same |

In one of the four sessions the payload of the task title turn arrived first and
was recorded as the result. Together with `session-pJ1JWw` that is two of six
short first requests. The adapter of 0.0.9 accepted an input that ends with the
turn marker. For the first turn no thread is established, so the thread of the
accepted payload became the session's thread.

The repair (`5e17336`) accepts an input only when it begins with Bridge's header
and ends with the marker. Its test replays the two payloads in the order that
recorded the title and fails without the repair. A Codex review through Agent
Bridge (`session-ZIrycu`) traced every production path and found the header in
front of each prompt. It found one case in which the stricter rule loses a
result: with `/ide` on, the TUI puts its IDE context in front of the message. It
also found that one test sent an unframed prompt and compared the notification
of a framed one. The extension (`b52ffb8`) accepts the prompt behind the IDE
context, with the wrapper taken from `codex-rs/tui/src/ide_context/prompt.rs`,
and the test now replays the argument that was queued.

Live:

| Build | Evidence | Result |
| --- | --- | --- |
| 0.0.9 code | `session-pJ1JWw`, `session-2qIKg5` and four more runs | Two of six short first requests recorded the title |
| Repair `5e17336` | `session-uwcQkK`, `session-hnJDFl`, `session-QuFhux`, `session-6A3uiN`, `session-2fRzWn`, `session-Ywub0u` | Six of six returned the answer |
| Release candidate, linked worktree | `session-nyxSJt`, `session-FR63X0`, `session-9ylPjW` | Three of three returned the answer |
| Release candidate, self-test with a local Codex daemon | `session-TXv9Kk` | Both requests returned the marker |

## The three features

#53, #54 and #55 were implemented by Codex sessions through Agent Bridge, each
in a worktree of its own. The owner decided two design questions afterwards:
the elapsed-time change keeps reading `created_unix_ms` as optional, and the
self-test runs in the ordinary state root by default with the private directory
as the option `--isolated`. The five branches merged without a textual conflict.
The merged code did not compile: the timeline passed the record times on as
required numbers. That was repaired on the release branch (`22672dd`).

Self-test, live with the release candidate:

| Provider | Mode | Evidence | Result |
| --- | --- | --- | --- |
| Claude Code 2.1.287 | default | `session-5aU43A` | Every step passed in 43.3 s |
| Claude Code 2.1.287 | `--isolated` | `session-O71WMr` | Every step passed in 37.7 s |
| Agy 1.2.14 | default | `session-xFslsi` | Every step passed in 58.8 s |
| Pi 0.99.2 | default | `session-Zo5WLc` | Every step passed in 11.0 s |
| Codex CLI 0.159.3, local daemon running | default | `session-TXv9Kk` | Every step passed in 25.7 s |
| Codex CLI 0.159.3, no local daemon | default | `session-VJ9pza` | `tell` ended as `unsupported`; exit code 1 after 21.4 s; session closed |

The timeline was run against the sessions of these checks. For `session-TXv9Kk`
it reported two completed requests with a recorded completion, 20047 ms and
4245 ms of elapsed time, and `derived_from` `result`; five request entries and
twelve session entries; `incomplete` false. Before the review repairs it was run
against two sessions of the 0.0.9 work, a closed Agy session with two requests
and a session whose initial input was withheld; both session directories were
byte-identical afterwards. The human output of `result` printed `Bridge observed
elapsed: 2498 ms` for a Pi follow-up.

## Review findings

Three reviews by Codex through Agent Bridge changed the release.

- `session-p4tWkE` on the first repair of #60: two defects that had to be
  repaired and one about the order of the checks, as described above. All three
  were repaired.
- `session-ZIrycu` on the repair of #61: the IDE context case and the test that
  fabricated an input. Both were repaired.
- `session-GQiTBV` on the three features at `22672dd`: eight findings. Repaired
  in the timeline: a record with invalid UTF-8 shown as observed; a replacement
  of a record between two reads that escaped the consistency check; reads without
  a bound; a `launch.log` line whose number made the query panic. Repaired in
  the self-test: commands waited for without a bound; an isolated cleanup that
  closed nothing when the private directory held two sessions. Repaired for the
  elapsed time: a completion journal whose event has no time passed the
  validation and could be published. Answered by a field: the request summaries
  of the timeline repeat what `result` reports, including its diagnostic for a
  launch whose deadline has passed; they now carry `derived_from`.
- Each repaired finding has a test that failed before the repair.
- No review ran after the repairs of the feature findings.

## Side effects

Seventy-two sessions were created in isolated state directories by the commands
of this work, and five more by the delegated sessions in state directories of
their own under the system temporary directory. All were closed explicitly. No
session created by anyone else was touched.

The local Codex daemon was started and stopped twice for the Codex self-test.
Each start left an update loop running, which was ended by its process id after
its command line and start time had been checked. Nothing was written to a
provider trust store. The probe directories and the worktrees of the work were
removed. The state directories that the delegated sessions created under the
system temporary directory were left in place.
