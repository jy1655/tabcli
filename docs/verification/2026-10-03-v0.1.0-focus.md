## 실제 iTerm2 타이핑 실패

사용자가 시험용 iTerm2 입력창에서 `a`를 연속 입력했다. 첫 시도는 검사 harness의
PATH에 Claude가 없어 세션 생성 전에 실패했다. 원본 근거를 보존하고 부모 PATH를
명시적으로 전달한 뒤 다시 실행했다. 이 첫 실패는 제품 실패로 세지 않는다.

두 번째는 제품 실패다. 버전만 바꾼 0.1.0 바이너리 SHA-256
`51063a09970b9b7e0e5649dd992e46e771fcccdd1c78cbe9b9ddc1d6ca45be94`가
15:42:09.201에 검사를 시작했다. 생성한 `session-sCCO3K`의 iTerm UUID는
`4BD22129-F81E-46DB-B4D3-961C46ACD456`이다. 이전 입력창 UUID
`EFB1EEE9-C3C0-4832-B730-6397AB88648C`에서 새 UUID로 잠시 선택이 바뀐 뒤
이전 창으로 돌아온 것을 native API가 기록했다.

이 정확한 세션 경로를 찾은 shell history에는 다음 시작 명령이 남았다.

```text

```

사용자 입력이 `write text`로 보내는 명령 앞에 붙었다. wrapper와 provider는
시작하지 않았고 30초 뒤 startup timeout으로 실패했다. 이후 cleanup은 PASS였다.
사용자는 이 시도 뒤 “진행했다”고 답했다. 입력창에서만 받은 byte·전경 앱·선택
sample을 기록했으며 전역 키 입력을 수집하거나 합성하지 않았다.

## iTerm2 수정 검증 중

수정은 iTerm2의 공식 생성 `command` 인자로 `/bin/zsh -l -i -c` bootstrap을
전달한다. 따라서 편집 중인 shell 명령줄에 시작 명령을 붙이지 않는다. profile의
custom command 대신 zsh login·interactive 시작 파일을 사용한다.

bootstrap은 기존 launch receipt·claim·status와 atomic `terminal.json`을 기다린다.
연결된 managed session과 iTerm2가 전달한 UUID가 일치한 뒤 자기 PTY의 초기 입력을
버리고 wrapper를 시작한다. 선택 복원과 binding 전에 provider를 실행하지 않으며,
취소·기한 만료·잘못된 binding에는 실행하지 않는다. 새 영구 protocol은 추가하지 않았다.

- 수정 전 private PTY 회귀: 실제 `a.` 명령 오류로 FAIL.
- 수정 후 같은 회귀: PASS.
- 연결 대기·취소·잘못된 binding·실제 foreground owner/shell attestation과
  초기 입력 버퍼 정리를 포함한 iTerm 선택 검사: 9 PASS.
- 수정본 SHA-256
  `b2d09b5e8015ac4cf0d8a313a5dee53550e631564d9ba73d384efcbfdc7a7dc1`의
  Fable self-test `session-pGKztV`: 최초 요청·결과, 공식 후속 요청·결과,
  cleanup 모두 PASS, 24,718ms. 기록된 owner/shell/provider 세 PID는 모두 없다.
- 동일 수정본의 사람 타이핑 재검사: iTerm2 입력창에서 iTerm2 세션 생성
  `session-d6L2L1`(15.242s), Terminal 생성 `session-ocOM5Y`(19.776s) 모두

## iTerm2 새 창 모드의 추가 복원

`new-window` 경로도 별도로 검사했다. 수정본2ee145cd의
`session-bWSbV9`는 왕복·cleanup은 PASS였으나, 새 창13124가 실행 중115개
sample에서 선택됐고 이전 WezTerm 대신 iTerm2가 전경이었다. 창 선택 복원이
이 경로에는 없었다.

이전 창을 기억하고 새 UUID가 선택돼 있는 동안만 복원하도록 수정했다. 전경 앱은
같은 AppleScript 실행 안에 원래 `NSRunningApplication` 객체를 보관해 복원한다.
PID를 나중에 다시 찾아 다른 프로세스를 선택하지 않는다. 사용자가 다른 앱·창·탭을
선택했거나 원래 앱이 종료됐다면 복원하지 않으며, 소유권 판단에는 사용하지 않는다.

첫 수정45ab856b의 `session-KmiKGz`는 창 선택은 돌아왔으나 앱 전경이 iTerm2에
남아 FAIL였다. 진단에서는 `NSWorkspace.frontmostApplication`이 생성 전 값을
계속 반환했다. [Apple 문서](https://developer.apple.com/documentation/appkit/nsrunningapplication)
에 명시된 main run loop 갱신을 처리한 뒤 전경을 다시 조회하도록 수정했다.
이는 surface 준비 상태를 시간으로 추정하는 gate가 아니다.

수정본79cbf58f의 `session-ahvxYA`는 23.875s에 최초·후속·cleanup PASS였다.
16:24:01.736 sample에서 새 창13170/iTerm2가 잡힌 뒤16:24:02.012에는 이전
창12275와 WezTerm 전경이 복원됐다. 90 sample 중89개는 WezTerm이었고,
`ask` 반환 전 복원된 뒤 왕복·종료까지 유지됐다. 기록된 owner·shell·provider
세 PID도 사라졌다. 약276ms 간격의 관찰이며 순간적인 포커스 이동을 없앴다는
뜻은 아니다. 실제 새 창 모드 타이핑과 최종 통합본 검사는 아직 남아 있다.

회귀 테스트의 수정 전 실패, 실제 script의 복원 판단을 mock OS 관측값으로 실행한
검사, 진단 fixture와 실패한 중간 후보까지 모두 원본으로 남겼다. 마지막으로 창을

이때 AppKit은 Terminal 전경 유지를, native 선택 sampler는 원래13087을
105회 보고했다. 생성 도중의 짧은 입력 노출은 이 sample 사이에도 발생할 수

## WezTerm 시작·선택 복원 수정과 실앱 검사

전달한다. `native-wezterm-host`가 기존 launch receipt·claim·status와 binding을

## Terminal 시작 경로 수정 후 자동 왕복

Terminal 2.15의 `do script`는 프로그램 인자 생성 API가 아니라 입력 전달이다.
Fable은 생성 시 한 번만 line-kill(`U+0015`) 뒤에 짧은 private bootstrap을
전달하도록 바꾸었다. `native-terminal-host`는 자기 controlling tty와 pending
launch·claim·status·binding을 확인한 뒤 입력을 비우고 wrapper를 시작한다.
기본 zsh의 emacs/vi 편집 모드 및 bash의 private PTY 회귀로 수정 전 `a.` 실패와
수정 후 시작 보호를 확인했다. 이미 Enter로 제출한 앞선 명령을 취소하는 기능은
아니며, line-kill을 바꾼 사용자 shell 설정까지 보장하지 않는다.

부모 통합본 `5046ff0000844f3d2a5a92abb26f98196cf41f38d5c0e35520791502f65c50e2`의
`session-aEGSeU`는 39.047s에 최초·후속·cleanup PASS였다. owner49274, shell48324,
provider49277은 종료 뒤 모두 부재였다. 이 자동 검사 중1287 foreground samples는
모두 `com.apple.loginwindow`였다. 따라서 이 결과는 왕복·정리 근거이며 잠금 해제
상태의 전경 복원·타이핑 근거가 아니다. 별도 입력창을 준비해 실제 사용자 입력을
기다리고 있다.

## Ghostty 시작 수정과 통합 소스 검사

Ghostty1.3.1은 child에게 terminal identity를 제공하지 않는다. Fable은 생성
command로 `native-ghostty-host`를 실행하고, binding 후 정확한 native terminal에
기존 claim token·session directory를 담은 frame을 한 번 전달하도록 바꾸었다.
host는 자기 PTY에서 이를 읽고 pending launch·claim·binding과 private script를
검증한 뒤 초기 입력을 비운다. 시작 명령이나 Enter는 입력하지 않는다. 초기
입력으로 `a.`가 생기는 private PTY 회귀는 수정 전 FAIL, 수정 후 PASS였다.

전경 복원은 nullable AppKit launchDate 대신 앱 객체를 보관한 동안 읽은 PID·bundle·
process start를 사용한다. `ps` start는 초 단위이며 close 소유권에는 사용하지 않는다.
바뀐 앱 또는 예상하지 않은 Ghostty 선택은 복원하지 않는다. 실제 macOS가 요청을
