## iTerm2 수정 검증 중

수정은 iTerm2의 공식 생성 `command` 인자로 `/bin/zsh -l -i -c` bootstrap을
전달한다. 따라서 편집 중인 shell 명령줄에 시작 명령을 붙이지 않는다. profile의
custom command 대신 zsh login·interactive 시작 파일을 사용한다.

bootstrap은 기존 launch receipt·claim·status와 atomic `terminal.json`을 기다린다.
연결된 managed session과 iTerm2가 전달한 UUID가 일치한 뒤 자기 PTY의 초기 입력을
버리고 wrapper를 시작한다. 선택 복원과 binding 전에 provider를 실행하지 않으며,
취소·기한 만료·잘못된 binding에는 실행하지 않는다. 새 영구 protocol은 추가하지 않았다.

## Terminal 시작 경로 수정 후 자동 왕복

Terminal 2.15의 `do script`는 프로그램 인자 생성 API가 아니라 입력 전달이다.
Fable은 생성 시 한 번만 line-kill(`U+0015`) 뒤에 짧은 private bootstrap을
전달하도록 바꾸었다. `native-terminal-host`는 자기 controlling tty와 pending
launch·claim·status·binding을 확인한 뒤 입력을 비우고 wrapper를 시작한다.
기본 zsh의 emacs/vi 편집 모드 및 bash의 private PTY 회귀로 수정 전 `a.` 실패와
수정 후 시작 보호를 확인했다. 이미 Enter로 제출한 앞선 명령을 취소하는 기능은
아니며, line-kill을 바꾼 사용자 shell 설정까지 보장하지 않는다.

부모 통합본 `5046ff0000844f3d2a5a92abb26f98196cf41f38d5c0e35520791502f65c50e2`의
`session-aEGSeU`는 39.047s에 최초·후속·cleanup PASS였다. owner49274, shell48324,
provider49277은 종료 뒤 모두 부재였다. 이 자동 검사 중1287 foreground samples는
모두 `com.apple.loginwindow`였다. 따라서 이 결과는 왕복·정리 근거이며 잠금 해제
상태의 전경 복원·타이핑 근거가 아니다. 별도 입력창을 준비해 실제 사용자 입력을
기다리고 있다.

## Ghostty 시작 수정과 통합 소스 검사

Ghostty1.3.1은 child에게 terminal identity를 제공하지 않는다. Fable은 생성
command로 `native-ghostty-host`를 실행하고, binding 후 정확한 native terminal에
기존 claim token·session directory를 담은 frame을 한 번 전달하도록 바꾸었다.
host는 자기 PTY에서 이를 읽고 pending launch·claim·binding과 private script를
검증한 뒤 초기 입력을 비운다. 시작 명령이나 Enter는 입력하지 않는다. 초기
입력으로 `a.`가 생기는 private PTY 회귀는 수정 전 FAIL, 수정 후 PASS였다.

전경 복원은 nullable AppKit launchDate 대신 앱 객체를 보관한 동안 읽은 PID·bundle·
process start를 사용한다. `ps` start는 초 단위이며 close 소유권에는 사용하지 않는다.

## Terminal 독립 리뷰의 한계 정정

Ghostty 작성자인 별도 Fable의 Terminal 시작·binding·flush·dispatch 검토는
**PASS**, 출시를 막는 코드 지적 없음이다. 이 리뷰는 commit24b4fbe의 파일
85411aa2에 적용하며, 앞선 사람 입력 검사는 부모가 별도로 기록한 증거다.

private PTY에서 기본 zsh/bash의 Escape·Ctrl-V가 line-kill 바로 앞에 오면
시작 명령이 실행되지 않는 경우를 재현했다. remap한 shell만의 한계가 아니므로
주석과 릴리즈 노트에 기본 편집기의 prefix/quote 상태도 명시했다. 이미 Enter로
제출된 명령은 취소할 수 없다는 기존 한계도 유지한다. 일반 문자 `a` 재검사와
이 특수 키 실패를 서로 대체하지 않는다.

또한 zsh에 running/suspended job이 있으면 host 거부 뒤 `exit`를 거부하고
prompt에 남을 수 있었다. bootstrap의 다음 줄이나 wrapper는 실행되지 않았다.
주석의 “항상 shell 종료”를 “wrapper 전 bootstrap 중단”으로 정정했다.
이후 Terminal 변경은 두 주석뿐이며 실행 코드는 바꾸지 않았다. bash의 빈 줄
line-kill bell과 rename 직후 sync 실패의 기존 binding race는 정보성 한계로 남겼다.

## iTerm의 일반 속성 조회 보정 — 실제 입력 대기

Fable은 응답하지 않던 수동 Apple event 생성을 제거했다. 최종 파일
`348f8074`는 iTerm이 반환한 `properties` record의 `frontmost`를 읽는다.
[AppleScript application 설명](https://developer.apple.com/library/archive/documentation/AppleScript/Conceptual/AppleScriptLangGuide/reference/ASLR_classes.html)의
직접 `frontmost` 조회는 앱에 event를 보내지 않는다. 반면 이 record의 필드는
설치된 iTerm dictionary의 `isActive` 값이다. 코드에 쓴 `pALL`·`pisf`와 일반
용어형은 iTerm dictionary에서 같은 script로 컴파일됨을 확인했다. 실제 handler를
record와 그 바깥의 값이 반대인 fixture에 실행하는 검사도 추가했다.

Fable의 최종 관련19검사, terminal module156검사(1 ignored), 의도적으로
잘못 바꾼27개 변형의 검출이 통과했다. 부모 Codex의 독립 소스 검토도 PASS다.
통합 실행 파일 `combined3/agent-bridge`의 SHA-256은
`875a22a814c28ce53a6257f5bd192a5d63942d33edf230f2eab2b3a44d3eb6f3`다.
이 소스의 전체 순차680 PASS/6 ignored와 Clippy·fmt·diff 검사가 통과했고,
빌드부터 검사 종료까지 소스 hash가 같았다.

이 실행 파일의 new-window `session-jcYh4e`는32.942s에 최초·공식 후속·종료를
통과했다. 실제 시작 시 사용 중이던 다른 앱에서 iTerm으로 갔다가275ms의 관측
간격 뒤 그 앱으로 돌아왔다. 전경1321표본 중1310개가 이전 앱, 11개가 iTerm이었다.
native 전후 선택은 같은 window12275/session0678CDDB였고, 생성한 session5C370C7C의
부재와 owner42703/shell41993/provider42705의 부재를 확인했다.

이 실행의 준비 절차에는 오류가 있었다. WezTerm 전경을 기대한 확인은 실제로
다른 앱이 앞에 있어 실패했지만, 다음 shell 줄의 실행을 막지 못했다. 준비 실패를
별도 보존하고, 실제 첫·마지막 표본과 native 기록으로 판정했다. 이 결과는 그때
관측한 다른 앱 복원만 입증하며 WezTerm 전경 재검사로 표시하지 않는다.

같은 소스의 `AB FOCUS FINAL iterm2`에서 tab-first·new-window 실제 입력 검사를
준비했다. 해당 사람 입력 결과와 최종 CI·게시 확인은 이 시점에 아직 대기 중이다.
다른 세 terminal의 최종 production 경로는 앞선 통합본과 같고, Terminal 변경은
검토 후 설명 주석뿐이다. source·runtime 대응은 `combined3/component-provenance.json`에
기록했다. 실행 중인 앱을 대상으로 한 검증이며 cold start·특수 state 경로의 새로운
실앱 검증으로 확대하지 않는다.

## 최종 iTerm 실제 입력 통과 — 네 터미널 수락 완료

18:29–18:30 KST에 위 `combined3` 실행 파일로 사용자가 두 단계의 실제 입력을
수행했다. `session-URa9ov`(tab-first)는16.400s, `session-oAWS8c`(new-window)는
15.757s에 최초 요청·공식 후속 요청·결과·cleanup을 모두 통과했다. 두 세션 모두
closed이며, 입력창은 각8초 구간에서 ASCII `a` 60/56바이트를 수신했다.
사전 입력과 다른 byte를 `a`에 합산하지 않았다.

타이핑 중 AppKit 전경은 각319표본 모두 iTerm이었다. native 선택은 tab-first의
64표본 모두 원래 시험창13678/sessionC0407B6A였다. new-window에서는 새
window13682/session9A4BB1B0가1표본, 원래 시험창이59표본이었으며 원래 창으로
돌아왔다. 사용자도 두 단계 뒤 **“돌아옴”**으로 확인했다. 이는 실제 입력 수신과
복원의 증거이며, 모든 키의 무손실 전달이나 표본 사이의 무전환을 뜻하지 않는다.

제품 두 surface와 기록된 owner·shell·provider6 PID의 부재를 별도로 확인했다.
완료한 입력 helper는 자기 종료 flag로 끝냈다. 이어 정확한 helper에 한정한 native
close는 오류를 반환했으나, 성공한 새 inventory에서 그 UUID와 PID의 부재를 확인했다.
오류 반환을 close 성공으로 바꾸지 않는다. 기존 사용자 iTerm session5671A62F는
보존됐다. 마지막 Fable `session-W5aEYw`의 결과를 읽은 뒤 explicit close했고,
그 UUID와 owner45621/shell44878/provider45623도 모두 없어졌다.

이로써 Terminal·WezTerm·Ghostty의 앞선 실제 입력 PASS와 최종 iTerm PASS가
모두 확보됐다. iTerm은 최종 binary875a22a8로 재검사했고, 다른 세 adapter의
실행 경로는 앞선 binary9d8cf8be와 같다(Terminal의 두 주석 변경만 제외).
공통 terminal 경로와 provider adapter도 동일하다. Fable 및 부모의 소스 검토,
최종680 PASS/0 FAIL/6 ignored·Clippy·fmt·diff PASS와 이 runtime 근거를
최종 후보에 연결한다. 최종 branch/main CI와 게시 결과는 별도 기록으로 확인한다.
