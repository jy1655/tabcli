## Live checks of #166 with candidate binaries

Two release builds of the #166 branch were copied outside `target/` and used as the launcher.

- Round one (command line only; sha256 `82338682…`): a managed Codex session on a Windows Terminal
  tab (`session-TN0kXZ`) still reported `PSModulePath` with
  `\\?\c:\program files (x86)\powershell\7\Modules`, `Compress-Archive` from a `-File` script
  failed with the module-load error, and `cargo test --test native_policy windows_release_packaging::`
  inside the session failed 2 of 2. The process tree showed the root `pwsh.exe` with the plain
  command line but the verbatim image path, because `CreateProcessW`'s application name still
  carried it. `self-test codex` with that binary passed (`session-UtUW67`).
- Round two (application name as well; sha256 `d3fe7ae2…`): the same check in `session-umOOY1`
  reported `PSModulePath` as
  `D:\...\PowerShell\Modules;C:\Program Files (x86)\PowerShell\Modules;c:\program files (x86)\powershell\7\Modules;C:\Program Files\WindowsPowerShell\Modules;C:\WINDOWS\system32\WindowsPowerShell\v1.0\Modules`
  (no verbatim entry), the script printed `compress ok`, and the two packaging tests passed inside
  the session (2 of 2). `self-test codex` with that binary passed all five steps
  (`session-PXGVSs`, 35.6 s). The user's own shell has the same `PSModulePath` as the round-two
  session.
- Not exercised: a console window of its own (every launch took the tab path), macOS and Linux
  (no code change there), Claude, Agy and Pi sessions (the forwarder change applies to every
  provider launched through the PowerShell forwarder, which the Codex npm shim is).

## Release candidate on this branch

`cargo build --release --locked` on `release/0.4.9` produced `tabcli 0.4.9` (3,450,880 bytes,
SHA-256 `2f97fb320dd60df1ba9e33e8b8d04e0ce07e4f6347df0f60426dbdb4777a8d8b`). That binary, copied
outside `target/`, passed `self-test codex --terminal windows-console --yolo` (39.5 s;
`session-irMgNX` closed) and `self-test claude` (30.7 s; `session-D2lO0C` closed), five steps each.
On the same branch the serial suite passed 795 tests with 0 failures and 5 ignored (638 unit, 9
context-result, 3 dead-owner-repair, 14 doctor, 2 interrupted-close, 12 launch-failure, 1 native-live
with 4 ignored, 26 native-policy including both Windows packaging tests, 59 observability, 5
process-env-policy, 16 search, 5 self-test with the subprocess fixture ignored, 5 third-party-notices),
Clippy with `-D warnings` was clean on the host and on the `x86_64-unknown-linux-gnu` and
`aarch64-apple-darwin` targets, and `cargo fmt -- --check` and `git diff --check` reported nothing.
The help fixture needs no edit for this release (#152), and the README check covers both READMEs
(#151); the only version edits were `Cargo.toml`, `Cargo.lock`, the CI release pins and archive
names, the two README Install sections, and the release notes.

## Rehearsal

The release workflow was rehearsed on this branch with `gh workflow run release.yml --ref
release/0.4.9 -f tag=v0.4.8` (run 38248541526). The first attempt failed in its Windows test job:
the v0.4.8 source's `close_deadline_console_helper_is_bounded` did not see Windows PowerShell print
within the test's 10 s bound on a runner whose serial suite took 596 s (recorded as #180); build and
publish were skipped. The rerun of the failed jobs (attempt 2) succeeded in all six jobs (validate,
the two test jobs, the two builds, publish), and the publish job skipped its two publication steps,
`Publish verified release assets` and `Verify draft assets and publish`, as a rehearsal must. The
release branch's own CI (pull request #179) is recorded on the pull request.
