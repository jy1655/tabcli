# Keyboard focus of new managed sessions — 2026-10-01

Source baseline: commit `53ca8f5` on branch
`fix/codex-follow-up-target-20261001`. The change recorded here is the work for
issue #58.

This record describes a source change, its tests and its live checks. It is not
a release, a tag, or an installed update. The installed binary is still 0.0.8.

## The problem

Every macOS launch script called `activate` and left the new surface selected.
A key typed at that moment went to the managed session instead of the user's
own tab. The launch command is typed into the new shell as text, so a key that
arrives first ends up in the same input line.

On 2026-10-01 keys that Agent Bridge did not send reached new managed sessions
three times. The source of the keys was not identified.

| Time (KST) | Session | Result |
| --- | --- | --- |
| 16:27:49 | `session-KbgbIY` (Agy, iTerm2) | The Agy workspace-trust dialog was approved by an Enter, 24 seconds after the session was created |
| 17:30:04 | `session-v8Ayr2` (Agy, iTerm2) | The same dialog was approved the same way, 3 minutes 23 seconds after the session was created |
| 17:57:46 | `session-MG4ifx` (Agy, iTerm2) | A character arrived before the launch command: the tab shows `A. '<session>/launch.sh'` and `zsh: command not found: A.`, and `ask` failed after 30 seconds with `provider launch timed out before startup was confirmed` |

## What the terminals allow

Neither iTerm2 3.7.3 nor Terminal.app 2.15 can create a surface without
selecting it. That limit shapes the change.

| Subject | How it was checked | Result |
| --- | --- | --- |
| iTerm2: an option to create a tab or window unselected | scripting dictionary | None. `create tab` and `create window` take a profile and a `command` only |
| iTerm2: a tab created in a window that is not the current one | AppleScript run | That window becomes the current window |
| iTerm2: `set current tab of <window>` | AppleScript run | Fails with `AppleEvent handler failed` |
| iTerm2: `tell <tab> to select` | AppleScript run | Selects the tab |
| Terminal.app: an option to create a window unselected | scripting dictionary | None |
| Terminal.app: `set frontmost of <window> to true` | AppleScript run | Brings that window to the front of Terminal's windows |

## The change

The change is confined to the macOS terminal modules for iTerm2 and
Terminal.app. No provider adapter and no shared transport was modified.

- The two launch scripts no longer call `activate`.
- Before creating the surface, the script remembers the surface that has the
  keyboard: the selected tab of the current window in iTerm2, the front window
  in Terminal.app.
- Right after the surface is created, the script selects the remembered
  surface again, but only while the new surface still holds the selection. A
  tab or window that the user chose in the meantime keeps the keyboard.
- Remembering and reselecting are best effort. Each sits in its own `try`
  block, and a failure never fails the launch.
- The remembered surface is never the surface the script returns. Ownership
  still comes only from the surface the script created: the new session's
  unique ID in iTerm2, the new tab's tty and its uniquely matched window ID in
  Terminal.app.
- The Ghostty launch script is unchanged and still activates Ghostty.
  `create_tab` for Ghostty fails before that script can run, so it has no
  effect in this candidate. A comment marks it for the time the adapter is
  enabled again.
- The Windows console launch is unchanged.

One limit remains. The new surface has the keyboard from its creation until it
is deselected. A key typed in that time reaches the managed session, including
a key typed before the launch command.

## Live checks

Host: macOS 26.5.2 arm64, iTerm2 3.7.3, Terminal.app 2.15, Agy 1.2.14 as the
managed provider, isolated state directory.

A sampler script read the selected session (iTerm2) or the front window
(Terminal.app) during the launch. The median sample interval was 84 ms for
iTerm2 and 50 ms for Terminal.app. The exposure is given as a range bounded by
the neighbouring samples.

The case in which the user switches before the script reselects was reproduced
by running the restore block of each script directly against the application,
with a selection change inserted before it. In iTerm2 the selection stayed on
the tab chosen in the meantime. In Terminal.app the window brought forward in
the meantime stayed in front. In the control run without a change, the
remembered surface was selected again in both.

Before the change, `create tab` in iTerm2 took 1.4 to 1.9 seconds when the load
average was above 4. The exposure is therefore longer under load than the
values in the tables.

All test sessions were closed explicitly.

## Review finding

The first version reselected the remembered surface unconditionally. A review
by Codex through Agent Bridge (`session-mwKfzO`) pointed out that this
overrides a selection the user makes between the creation and the reselect.

The same review showed that the test was too loose. It still passed with an
`activate` added after the restore block and with the owned session taken from
the remembered tab.

The final version reselects only while the new surface holds the selection.
The test now forbids the word `activate` in both scripts and lists every line
that uses the remembered surface or assigns the owned one. The second review
round approved the final version. It suggested one more assertion, which was
added: the test also lists every line that assigns the iTerm2 target window.

## Not verified

- Whether iTerm2 or Terminal.app stays behind another application. The screen
  was locked during every live check, so the frontmost application was
  `loginwindow`. Each application reported `frontmost` as false in every
  sample, which does not settle the question. This needs one run with the
  screen unlocked.

- Keys typed while the new surface has the keyboard. They still reach the
  managed session.
- Issue #58 is not closed by this record.

## Observations outside this change

One Terminal.app launch (`session-y5Wpkl`) failed with `Agent Bridge could not
prove the newly created Terminal.app window`. A leftover window whose shell had
exited still reported the tty `/dev/ttys003`, the same name the new tab
received, so the proof matched two tabs. The new window stayed open without a
managed session to own it and was closed by hand. The later Terminal.app checks
ran with that tty name occupied.

A `close` sent by script to a Terminal.app window while its shell still has
child processes leaves the window open, and later `close` commands for that
window have no effect. Two experiment windows of this task were left in that
state, together with one empty iTerm2 window that is waiting for a
confirmation. They could not be dismissed while the screen was locked.
