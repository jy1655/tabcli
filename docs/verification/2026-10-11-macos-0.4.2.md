# Terminal Agent Bridge 0.4.2: macOS verification

## Candidate and environment

Production source: main `5d8c1d1140add1efc237d9529e4cd0df00ae6f84`, the merges of pull requests
#114 (close of a session whose surface vanished while its owner lives, #101) and #115 (close
deadline, busy WezTerm, #110). The release branch adds the version, the release notes and this
record only. Rust 1.98.1 on Apple Silicon macOS 26.6.2; WezTerm 20240203-110809-5046fc22, iTerm2
3.7.3, codex-cli 0.162.1, Claude Code 2.1.296, Pi 1.0.4, Agy 1.3.3. The screen was unlocked for
every live check below.

## Close of a session whose surface vanished (#101)

Run on 2026-10-11 between 11:04 and 11:06 KST with a release build of the #101 branch rebased on
main `c93cb63` (commit `1b68068`), before the close-deadline change. iTerm2 had been quit by the
operator before the run, so iTerm2 was cold-started by the first launch.

| Case | Result |
| --- | --- |
| iTerm2 killed with SIGTERM; its session server kept Bridge's process and Codex alive; close while iTerm2 was not running | `closed`, the process group gone, iTerm2 not started, reason "the surface was proven absent while its owner was live; the owner was ended" |
| iTerm2 killed, then started again by another launch, which restored the tab under a new unique id on the same tty; close | `closed`, the process group gone, the restored tab gone, the same reason |
| Normal close of a live iTerm2 surface | `closed` without a reason; the processes ended through the hangup within about five seconds |

The teardown with the close deadline of #115 is covered by unit tests only; iTerm2 was not killed
again for this record.

## Close deadline (#110)

With a release build of the #110 branch (13:58 to 14:01 KST): `ask` and then
`close-session --timeout-secs 20` closed a WezTerm session in 0.33 s, a Terminal.app session in
1.1 s and a Ghostty session in 1.64 s. `close-session --timeout-secs 1` on a Terminal.app session
ran out at 1.04 s during settlement, after the tombstone was written; the error said that the
close was not confirmed and that terminal-side work may have happened, and a rerun closed the
session. That run printed the expiry message twice, fixed before merging. With the 0.4.2
candidate, `close-session --timeout-secs 30` closed a WezTerm session in 0.33 s. A busy WezTerm GUI
was not reproduced.
