Each row is one `self-test --workspace <checkout> --terminal windows-console --json`,
using the ordinary state root and no `--yolo`. Each passed initial delivery, initial
result, follow-up delivery, follow-up result and cleanup; every created session was closed.

The two Claude version strings are what the separate runs reported. This verification
did not invoke a provider updater. Existing unrelated sessions were not closed.

Two unsuccessful preflight attempts preceded those passes. The initial environment had
a PowerShell `codex` function but no Codex executable on an absolute PATH entry, so Bridge
refused before creating a session. Prepending the npm directory resolved Codex but selected
an old npm Claude shim (2.1.226), which Bridge correctly refused as unsupported. Appending
that directory to the verification process's PATH preserved the native Claude executable
and exposed Codex. No persistent PATH, shell profile or permission setting was changed.

These runs used the existing workspace approvals. They do not establish a new live
verification of trust-dialog approval, revocation, or launch races; the consent component
tests cover those programmed cases. No claim about #260's native completion route follows
from these tests. Raw reports and logs remain private in the checkout's
`.git/windows-verification-20261022/`, outside build output.
