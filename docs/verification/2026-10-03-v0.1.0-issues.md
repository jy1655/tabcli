## #69: surface 보존과 내부 대기 실패 분리

owner가 종료됐어도 창의 부재를 증명할 수 없으면 macOS repair는 handle을 보존한다.
이때 상태만 검사하던 `ask`/`tell` 내부 대기는 owner 종료를 timeout으로 가렸다.
이제 완료 복구·결과 회수를 먼저 수행하고, 남은 대기에서 PID가 실제로 죽었으면
`no longer running`을 보고한다. status 대기의 stale `ready`도 검사하지만,
현재 macOS provider는 초기 입력을 인자로 전달하므로 이 helper를 호출하지 않는다.
현재 macOS 제품 경로의 수정은 event 대기이며, 다음 입력의 소유권 검증은 기존 경로다.

창의 handle·close intent·pending claim은 이 진단으로 소비하지 않는다.
PID가 살아 있거나 신원을 확인할 수 없는 경우를 사망으로 바꾸지 않는다.
공개 `result --wait`와 query 구현, provider의 완료 identity는 변경하지 않았다.
오류 맥락에서 창이 계속 열려 있다고 단정하던 문구도 제거했다.

새 regression은 expired deadline으로 오류 우선순위를 결정적으로 검사한다.
Terminal.app·Ghostty·WezTerm·Warp 각각에서 handle, closing handle, close intent를
보존하는 두 대기를 검사하며 실제 terminal/provider를 실행하지 않는다.

- 수정 전: 새 event/status 회귀 **2 FAIL**, 기능 대조군 **2 PASS**.
  필터에 같이 선택된 session-id 검사 1개도 PASS였다.
- 수정 후: 같은 `internal_` 선택 **5 PASS**(session-id 검사 1개 포함).
- 최종 수정의 `dead_owner` 선택: **9 PASS**, handle 없는 기존 종료 경로 포함.
- 완료 journal 복구와 이미 게시된 결과는 owner 사망보다 먼저 회수했다.
- 실제 900초 대기를 측정하거나 Warp runtime을 검증한 결과가 아니다.

## #68: 시작을 확인한 뒤 timeout 검사

기존 fixture는 daemon probe와 queue 시작에 500ms를 함께 사용하면서
`queue-started`가 존재한다고 가정했다. fake queue의 시작을 650ms 늦추면
수정 전의 같은 assertion이 실패했다. 이는 해당 가정의 재현이며, 10월 2일
실패 당시의 실제 지연이나 원인을 사후에 증명한 것은 아니다.

보강한 fixture는 5초 안에 descendant의 시작을 확인한 뒤 테스트 전용 hook으로
deadline을 만료시킨다. 실제 timeout·process-group 종료 경로를 실행하며,
descendant가 열어 둔 FIFO의 마지막 reader가 사라졌는지 확인한다. 종료를
고정 sleep 뒤 marker 부재만으로 추정하지 않는다. delivery-uncertain,
terminal fallback 금지, pending metadata와 정확한 claim token 보존도 검사한다.

650ms 시작 지연을 유지한 보강 테스트는 **1 PASS**다. hook은 Unix test 빌드의
해당 테스트 thread에서만 활성화되며, 제품 빌드의 공유 deadline은 바뀌지 않는다.
Claude·Agy·Pi adapter에는 변경이 없다.

독립 리뷰 후 hook 소비 assertion, setup 오류 진단, 실패 시 FIFO를 해제하는
fixture RAII 정리를 추가했다. hook 미호출·6초 시작 지연·그룹 대신 leader만
종료하는 세 가지 변이를 별도 archive에서 실행했다. 각각 의도한 이유로 실패했고
남은 fixture process는 0개였다. 정상 fixture는 PASS다.

## #64: 닫힌 창의 재등장과 close 재시도 분리

Claude Fable이 두 원인을 재현했다. Terminal은 닫은 창을 잠시 목록에 보존한다.
탭은 없고 화면에 표시되지 않지만 `window 1`일 수 있다. 다음 launch의 포커스
복원 코드가 그 창을 `frontmost`로 설정하면 Terminal은 빈 창을 다시 표시했다.
복원 대상 조건에 `visible is true`를 넣어 이미 닫힌 창을 다시 열지 않도록 했다.
선택한 창이 생성 도중 닫힌 경우도 같은 조건으로 보호한다.

별개로 기존 cleanup은 close가 성공해도 목록에 남은 창을 다시 닫으려다가
`window no longer holds its tab`으로 실패했다. 이제 **같은 close transaction의
CLOSE가 `closed`를 반환한 직후**에만 WAIT가 기록된 창의 `tabs=0`과
`visible=false`를 확인해 `closed`를 반환한다. `missing`과 구분하며, 일반 조회의
목록 부재 조건은 그대로다. 보이는 빈 창, 탭이 남은 창, 읽기 오류, close를
확인하지 못한 창은 성공으로 바꾸지 않는다. script 전후 앱 identity 확인과
CLOSE/VERIFY의 기존 소유권 검증도 유지한다.

- Part 1 회귀: 이전 OPEN에서 닫힌 창을 frontmost로 만든 **1 FAIL** → 수정 후
  관련 **25 PASS**. 표시 중인 창 및 생성 중 닫힌 창 대조군 포함.
- Part 2 회귀: 이전 close 흐름에서 **3 FAIL / 4 PASS** → 최종 관련 **29 PASS**.
  실제 script replay, 읽기 오류·보이는 빈 창 거부, 앱 identity 재확인 포함.
- Terminal 2.15 / macOS 26.5.2의 native API probe에서 task 소유 shell만
  `exit 1`로 끝낸 뒤 제품 script를 실행했다. A=12674는 close 후 30초간
  invisible/zero-tab으로 목록에 남았다. 이전 WAIT는 `present`, 새 WAIT는
  실제 close 응답이 있을 때만 `closed`였다.
- patched OPEN으로 B=12678을 열었을 때 A는 재등장하지 않았다. B를 닫고
  unpatched OPEN으로 C=12679를 열자 B가 `visible=true`, `tabs=0`으로
  다시 나타났다. 새 WAIT도 이 표시 중인 B를 `present`로 거부했다.
- probe 종료 시 B/C는 invisible/zero-tab이었다. 이는 Terminal API 관찰이며
  물리 화면 확인이나 provider 왕복 증거가 아니다. 프로세스 신호·앱 전체 종료는
  사용하지 않았고 기존 사용자 창은 없었다.

이 증거가 이전 두 실험의 PASS 철회를 취소하지는 않는다. 재등장 원인을 별도로
재현하고 수정한 새 후보다. close 도중 프로세스가 중단되어 이후 transaction에서
이미 탭 없는 창을 만난 경우는 여전히 거부하며 handle을 보존한다.

독립 리뷰에서 lookup miss의 실제 오류 번호가 미확인이라는 지적을 받았다.
부모의 읽기 전용 조회에서 Terminal 2.15는 없는 window의 `whose` 조회에
`-1719`를 반환했다. `40bf259`는 기존 `-1728`뿐 아니라 이 오류도 다음 목록
조회로 재확인한다. 오류 자체를 `missing` 또는 `closed`로 인정하지 않는다.
목록에서 실제로 사라진 경우와 여전히 남은 경우를 추가한 회귀는 수정 전
**1 FAIL** → 수정 후 관련 **4 PASS**였다. 다른 읽기 오류는 계속 전파한다.

### Terminal / Claude 실앱 검사

`cb38e4f` 바이너리
`bb0cd39e085132c8cce3de0e3a63c627565c0f509bfd5d8064fc48f7d9790aef`로

1. 형제 세션 `session-kl0rTH`(window 12705, `/dev/ttys013`)의 marker 응답을

   최초 요청·결과, 공식 후속 전달·결과, cleanup **모두 PASS**, 23,264ms였다.
2. cleanup 후 12705는 여전히 표시 중이며 탭 1개였다. 형제 세션의 owner

세 세션은 모두 closed/unclaimed다. 이는 전체 provider lifecycle와 Terminal API의

수정했다. 제품 실패로 세지 않고 최초 오류 log도 보존했다.

오류 번호 보정 `40bf259e147c43b8b3adcaa4b5537e4b82847cf5`의 최종 바이너리
