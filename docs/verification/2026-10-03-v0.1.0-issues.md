## #69: surface 보존과 내부 대기 실패 분리

owner가 종료됐어도 창의 부재를 증명할 수 없으면 macOS repair는 handle을 보존한다.
이때 상태만 검사하던 `ask`/`tell` 내부 대기는 owner 종료를 timeout으로 가렸다.
이제 완료 복구·결과 회수를 먼저 수행하고, 남은 대기에서 PID가 실제로 죽었으면
`no longer running`을 보고한다. status 대기의 stale `ready`도 검사하지만,
현재 macOS provider는 초기 입력을 인자로 전달하므로 이 helper를 호출하지 않는다.
현재 macOS 제품 경로의 수정은 event 대기이며, 다음 입력의 소유권 검증은 기존 경로다.

창의 handle·close intent·pending claim은 이 진단으로 소비하지 않는다.
PID가 살아 있거나 신원을 확인할 수 없는 경우를 사망으로 바꾸지 않는다.
공개 `result --wait`와 query 구현, provider의 완료 identity는 변경하지 않았다.
오류 맥락에서 창이 계속 열려 있다고 단정하던 문구도 제거했다.

새 regression은 expired deadline으로 오류 우선순위를 결정적으로 검사한다.
Terminal.app·Ghostty·WezTerm·Warp 각각에서 handle, closing handle, close intent를
보존하는 두 대기를 검사하며 실제 terminal/provider를 실행하지 않는다.

- 수정 전: 새 event/status 회귀 **2 FAIL**, 기능 대조군 **2 PASS**.
  필터에 같이 선택된 session-id 검사 1개도 PASS였다.
- 수정 후: 같은 `internal_` 선택 **5 PASS**(session-id 검사 1개 포함).
- 최종 수정의 `dead_owner` 선택: **9 PASS**, handle 없는 기존 종료 경로 포함.
- 완료 journal 복구와 이미 게시된 결과는 owner 사망보다 먼저 회수했다.
- 실제 900초 대기를 측정하거나 Warp runtime을 검증한 결과가 아니다.

## #68: 시작을 확인한 뒤 timeout 검사

기존 fixture는 daemon probe와 queue 시작에 500ms를 함께 사용하면서
`queue-started`가 존재한다고 가정했다. fake queue의 시작을 650ms 늦추면
수정 전의 같은 assertion이 실패했다. 이는 해당 가정의 재현이며, 10월 2일
실패 당시의 실제 지연이나 원인을 사후에 증명한 것은 아니다.

보강한 fixture는 5초 안에 descendant의 시작을 확인한 뒤 테스트 전용 hook으로
deadline을 만료시킨다. 실제 timeout·process-group 종료 경로를 실행하며,
descendant가 열어 둔 FIFO의 마지막 reader가 사라졌는지 확인한다. 종료를
고정 sleep 뒤 marker 부재만으로 추정하지 않는다. delivery-uncertain,
terminal fallback 금지, pending metadata와 정확한 claim token 보존도 검사한다.

650ms 시작 지연을 유지한 보강 테스트는 **1 PASS**다. hook은 Unix test 빌드의
해당 테스트 thread에서만 활성화되며, 제품 빌드의 공유 deadline은 바뀌지 않는다.
Claude·Agy·Pi adapter에는 변경이 없다.
