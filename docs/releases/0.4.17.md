# Terminal Agent Bridge 0.4.17

0.4.17 moves Codex completion off the legacy `notify` command line and onto Codex's first-party
lifecycle hooks and its own terminal record, which closes the stranded Windows completion of
#127 (#250), and refuses a Windows follow-up whose `codex queue` command line would exceed the
process command-line limit before anything is sent (#251, #252). Records written by 0.4.x are
read as before; this release adds Codex-only records to the session directory
(`codex-launch-mode.json`, `codex-turn-<claim>.json`, `codex-candidate-<claim>.json`,
`codex-notify-<claim>.json`, `codex-observer-<claim>.json`) and one optional field,
`provenance`, on the completion event. A 0.4.16 or older binary reads such an event but drops the
field: do not use an older separate binary for commands or recovery on a session this release
journaled, and do not downgrade while such a session is open (upgrading is supported).

## Changes

- Codex lifecycle hooks (#127, #250). With stable codex-cli 0.163.0 or newer, the
  `codex-lifecycle-hooks` setting on (the default) and an executable path the shells run
  unquoted, every Codex launch injects a `UserPromptSubmit` and a `Stop` command hook as one
  process-local `-c hooks=` value, together with the two trust hashes Codex computes for them
  (SHA-256 over the normalized handler; the four values Codex wrote on Windows and macOS are
  pinned by tests). `UserPromptSubmit` binds the current claim to Codex's thread, turn and
  transcript when the prompt carries Bridge's framing and marker; `Stop` is recorded as a
  candidate only, because another Stop hook can continue the same turn; a bound claim settles
  only from the rollout transcript's `task_complete` or `turn_aborted` for the bound turn, read
  by a per-session watcher from byte zero as strict newline-terminated JSON with identity and
  length checks, and a malformed attribution field suspends the claim instead of deciding it.
  `notify` remains the route for claims that never got a hook (setting off, Codex below
  0.163.0, a prerelease, an unavailable launcher, hooks disabled in Codex) and is evidence only
  for a bound claim. The injection decision is recorded at launch in `codex-launch-mode.json`.
  Documented in [docs/providers.md](../providers.md); the boundary is in AGENTS.md.
- Windows initial paste for injected launches (#127, #250). Hash drift or an unrelated untrusted
  hook opens Codex's startup hook-review picker, which Bridge never answers. On native Windows a
  launch recorded as injected pastes nothing until the empty composer row is visible, whatever
  the stored workspace trust says, and names the picker in the deadline error when the last
  screen showed it.
- Doctor (#127, #250). `doctor <session>` reports `codex_lifecycle`: the launch-mode record, the
  binding, the Stop candidate, the observer state and the committed terminal outcome of this
  session's records. `doctor … --probe` adds `codex_hook_trust`: the installed Codex's own
  `hooks/list` answer for the two keys Bridge would inject, with the expected hash, so a
  normalization drift is visible without a launch. The notify payload budget applies only while
  a request may still depend on notify. Documented in [docs/cli.md](../cli.md).
- Settings (#127, #250). `settings codex-lifecycle-hooks on|off` controls injection for new
  Codex launches; `off` returns them to notify only.
- Queue follow-up size on Windows (#251, #252). `tell` runs `codex queue --thread … --message
  <framed prompt>`, and Windows refuses a process command line of 32,767 UTF-16 units or more.
  Bridge now measures the command line it is about to start and refuses before spawning or
  recording anything, naming the measured size and the limit; the session stays `ready`. The
  second hop that Codex's own launcher makes is not measured. Documented in
  [docs/providers.md](../providers.md).
- Dependencies. `sha2` (and its transitive crates) are added for the trust hash;
  `THIRD_PARTY_NOTICES.md` is regenerated.

## Why

Codex 0.163.0 ships Claude-compatible lifecycle hooks that deliver their payload on stdin and
marks `notify`, which hands the whole payload to the command line, as legacy. On native Windows
that command line stranded every long Codex turn (#127). The hooks give the turn's identity
before the answer exists, but `Stop` is not the end of the turn, so the terminal record is
Codex's own rollout; the design was criticized twice by an independent model review before
implementation and the branch was reviewed per round and once as a whole. The queue limit was
found while verifying the long-payload scenario live.

## Verification

See the [Windows live record](../verification/2026-10-18-windows-127-codex-lifecycle-hooks.md)
of 2026-10-18 (codex-cli 0.163.0): every bound claim settled from the transcript; the #127
reproduction (a 25,463-character prompt with a 10,092-character answer) completed with no
notify record; a steered TUI message joined the bound turn; a user Stop hook's block continued
the turn and only the final answer was published; a model error failed from
`task_complete{error}`; the setting off and Codex's hooks feature off settled through notify; an
untrusted hook's picker was named by the Windows gate with nothing pasted; `self-test codex`
passed. The queue refusal of #251 is covered by deterministic tests and by the live failure that
found it; see the pull request. Each pull request's six CI jobs passed before merge. Not
verified: Esc during post-turn compaction, a Bridge hash-drift build, and every macOS scenario
(skipped by the owner's decision; macOS keeps the same code path with the argument-delivered
initial prompt).

The Windows console large paste (#124), the Claude adapter's first-Stop settlement (#249),
Pi-owned records for the extension's claim and cancel reads (#196), Codex, Claude and Agy usage
(#55), the child-to-parent question channel (#189), the Ghostty cold launch (#104), Warp (#63,
#87), workspace-trust consolidation evidence (#28), Linux transport (#6) and the reopen
pre-launch window (#245) remain outside this release.
