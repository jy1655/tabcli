# Terminal Agent Bridge 0.4.37

0.4.37 makes the Codex question notice opt-in (#353), ships the general delegation rule in
the installed skill (#354), and closes the first cards of the 2026-11-06 architecture review:
one owner for the hooks Bridge injects into Codex and for the rule that decides them (#355),
one bounded reader for the Codex launch records (#360), the help Usage block rendered from the
command contracts (#356), the surface probe's owner requirement stated beside the probe (#358)
and a typed launch verdict (#357). Two fixes follow from the same review: the self-test report
keeps the terminal kind of a session whose handle was consumed (#359), and `describe` names
every command outside the common JSON envelope (#361). No transport was added and no command
sends input it did not send before.

## What changes for a caller

- **Codex question notice is off by default.** A state root that never set
  `codex-question-notice` stops injecting the `PreToolUse` notice hook into new Codex launches;
  `tabcli settings codex-question-notice on` restores it. Claude's question deflection keeps its
  default, on. See [Codex question notice](#codex-question-notice-is-opt-in-353).
- **`describe` lists its commands in the help's order**: `reopen`, `sessions` and `status` now
  come before `inspect`, and `consent` and `settings` after `doctor`. Entries are identified by
  `name`.
- **`describe` and `<command> --help` carry more notes**: the common output note and the
  `doctor`, `sessions`, `prune-sessions` and `close-session` contracts now say which commands
  print JSON without the common envelope and which report failures on stderr only.
- **`doctor --probe`** lists the `codex_hook_trust` rows in the order of the injected value
  (`stop`, `user_prompt_submit`, `pre_tool_use`), and a `hooks/list` reply that lacks several of
  Bridge's keys names the `stop` key first in its error.
- **Codex launch records** (`codex-launch-mode.json`, `codex-question-notice.json`) are read
  within a 64 KiB bound and as strict UTF-8. A record over the bound, or one with invalid UTF-8,
  is unreadable where it was accepted before.
- **`self-test --json`** reports `terminal` for a session whose terminal handle was already
  consumed by a close, where it reported none.

Everything else below keeps its public JSON, text output, error messages and record schemas.

## Codex question notice is opt-in (#353)

0.4.36 shipped `settings codex-question-notice` with the default on. The hook only adds advice
for the model, which a caller may not need, so it is now opt-in: without the setting a launch
records `not_injected` with the reason `settings_off` once the earlier gates pass, and carries
only the two lifecycle hooks. With the setting on, the hook, its trust hash, the launch record
and the `answer_after_turn` capability are what 0.4.36 shipped. `doctor --probe` proposes the
third hook only for a launch that would inject it: `codex-lifecycle-hooks` and
`codex-question-notice` both on and a stable Codex 0.166.0 or newer. A session already launched
keeps the decision in its own launch record. See [CLI](../cli.md#question-notice).

## Delegation rule in the installed skill (#354)

The `agent-bridge` skill that the Claude, Codex, Agy and Pi integration packages install now
states when to use Bridge: for a child on another provider than the host, or when the user asks
for Agent Bridge, `tabcli` or a terminal session to watch; for a child on the host's own
provider the host uses its own subagents. A request for subagents or parallel work alone does
not select Bridge. Launch details such as the terminal, the permission mode, the model, the
effort and a session budget stay in the user's own instructions, which win where they differ.
The integration is still instructions only: no hook, MCP server or system prompt. See
[integrations](../integrations.md).

## Codex hooks and launch decisions (#355, #360)

`codex/hooks.rs` now holds the hooks Bridge injects as one closed set (Stop, UserPromptSubmit
and the `PreToolUse` question notice) and one eligibility rule over the Codex version, the two
settings and the hook launcher. The `-c hooks=` value, the hook-trust probe and the native hook
dispatch all go through the set, and a launch and `doctor --probe` ask the same rule, where the
probe kept a second spelling that had drifted once (#351, fixed in #353). The value Bridge
passes to Codex is byte-identical, with and without the notice hook, and so are the two launch
records, their reasons and the order of the gates.

The two launch records now have one owning module, `codex/launch_decision.rs`, and one reader
that answers absent, unreadable or present. Every caller keeps what it did with each answer:
with an unreadable record the initial send refuses as not sent, the readiness wait returns the
error, `inspect` reports the question capability as unknown, the doctor's lifecycle row reports
the record unreadable, and the notify payload budget check goes on as if nothing was injected.
An absent record still means a session launched before the record existed.

The reader is bounded and strict where the old one was not: 64 KiB and strict UTF-8. The bound
is 64 KiB because the lifecycle record carries the whole output of `codex --version`; a launch
whose version output, JSON-escaped, is larger than about 65,400 bytes would write a record its
own reader refuses.

## Command contracts and help (#356, #361)

The help text's Usage block is rendered from the command contracts that `describe` publishes,
through the one synopsis format that `describe`'s text mode and `<command> --help` use, so a
synopsis is written once. The rendered help equals the previous handwritten text byte for byte.
The registry's public entries were reordered to the help's order to make that so, which changes
the order of `describe`'s commands. A public command is now one that has a contract; the
separate hidden flag is gone.

`describe`'s output contract said that only `consent` and `settings` deviate from the common
JSON envelope. Its common note now says what the commands do: `consent`, `settings`,
`sessions`, `prune-sessions` and `close-session` print JSON without `schema_version`;
`self-test` reports `outcome` instead of `ok`; those commands and `doctor` report errors on
stderr without a JSON error object; and with `--json` an argument-parsing failure prints a JSON
error object only for `describe`, `hold`, `cancel`, `screen`, `wait`, `status` and `search`.
The `doctor`, `sessions`, `prune-sessions` and `close-session` contracts each describe their own
JSON. No command's behaviour or output shape changed. See [CLI](../cli.md#discover-the-command-contract).

## Observation (#358, #357)

`inspect`'s `capabilities.tell` judged the owner side of `tell`'s surface ownership check with
its own copy of what the platform probe requires. That requirement is now stated beside the
probe in `terminal/ownership.rs`, over the owner attestation, and the query only maps the answer
to its reason codes. A test runs the real attestation and the real macOS probe on the same
processes and requires them to agree; the Windows counterpart runs on the Windows CI runner.
`inspect`'s output is unchanged.

One limit is now written down and not fixed: an attestation does not say which control fields
an owner record holds, so a macOS record with its birth and only some of its TTY and
process-group fields is reported as passing while `tell`'s probe refuses it. Current writers
record all the fields.

The launch verdict (`launch_uncertain`, `launch_failed`, `launch_timeout`) travels as a type
from the launch record to `status` and `doctor`, which map it exhaustively where they looked the
name up at run time. `wait` takes the object it holds for a request whose session stays busy
from the module that renders every other Request. Names and output are unchanged.

## Fix: terminal kind after a close (#359)

A close leaves `terminal.closed.json` as `{"consumed": true, "terminal": <kind or null>}`, with
a `reason` on macOS. The reader the self-test uses decoded that record as a terminal handle,
whose session id is required, so the read always failed and the self-test report lost the
terminal kind of a session whose handle had been consumed. The reader now decodes the shape the
close writes. Every earlier version wrote this shape, so records left by an earlier binary read
the same way.

## Verification and upgrade

Before the version bump, each change passed the complete local Rust suite on macOS and the CI
jobs of its pull request on Linux, macOS and Windows, and the main commit that holds all of
them passed CI. With the version bump the complete local Rust suite passed on macOS
(1,675 passed, 6 ignored) and the Python script suite passed (109 run, 2 skipped). Two results came from the
Windows CI runner and not from a Windows PC: the surface probe's Windows parity test (#358)
passed there, and a new `wait` test first failed there because it locked a file opened for
append only, which Windows refuses; the test was corrected before the merge (#357).

No authenticated provider session and no terminal surface was exercised for this release on
macOS or on native Windows. That covers the Codex launches with and without the notice hook,
`doctor --probe` against an installed Codex, and any host loading the new skill text. The
packaged 0.4.37 release's runtime is not verified by these notes; those checks are separate and
recorded outside this repository.

After the upgrade, a new Codex launch from a state root that never set `codex-question-notice`
carries no notice hook. A session launched by an earlier binary keeps its launch decision. The
[open-session upgrade notes](0.4.25.md#upgrade-notes) still apply. Do not downgrade a binary
used by an open session. The release includes macOS and Windows CLI archives and Claude, Codex,
Agy and Pi integration packages with checksums. Integration packages contain instructions, not
the engine binary; updating an integration takes effect in new host conversations.
