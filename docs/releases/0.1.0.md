# Agent Bridge 0.1.0

0.1.0 adds macOS terminal selection and opening modes, restores the Ghostty
adapter, and fixes Terminal.app cleanup and waits for an ended session.
Provider messaging and result identity continue to belong to each provider's
adapter.

## macOS terminals and opening modes

- `--terminal` accepts `ghostty`, `iterm2`, `terminal`, `warp`, and `wezterm`.
  The explicit choice overrides the invoking terminal's environment. An
  adapter error is reported instead of silently switching applications.
- `agent-bridge settings macos-open-mode tab-first` is the default. A safe,
  uniquely identified existing window receives a new owned tab where the
  terminal's native API supports it. `new-window` requests a separate window.
  The setting affects creation; it never changes an existing session's close
  authority.
- Terminal.app always opens a new window because its native scripting API
  does not create tabs. Existing tabs are never reused to simulate this.
- WezTerm uses its official CLI and a verified local GUI socket. A tab in a
  shared GUI is closed by its exact pane identity; the shared GUI and sibling
  panes remain. A new private GUI is used when there is no safe existing
  target, or when `new-window` is selected. An uncertain creation is not
  retried or treated as permission to close a guessed pane.
- Ghostty uses its native scripting API. A newly returned surface must also
  have a ready terminal model before it can be bound and started. Metadata
  alone is insufficient. The adapter restores the previous tab only while
  the new tab is still selected and preserves later user-created splits.
- Warp uses official Control and launch URI interfaces when the installed
  channel exposes the required runtime capabilities. Actual Warp runtime
  acceptance remains deferred; it is not a verified terminal in this release.
  Terminal-based Agy/Pi follow-ups and automatic workspace-dialog
  responses are not supported through this adapter.

Terminal scripting still needs the application's own settings and macOS
Automation permission. Agent Bridge does not change those permissions. See
[macOS setup and live checks](../macos-permissions.md).

## Startup keys and focus restoration (#58)

iTerm2 and WezTerm now receive the startup program through their native creation
arguments. Their launch hosts wait for the recorded surface binding and discard
input queued during creation before running the provider. A typed character
cannot become a prefix of the startup command.

Ghostty also starts its host through the native creation command. The host reads
a launch frame addressed to its bound terminal, checks the existing pending
launch records, and discards queued input before sourcing the launch script.
There is no typed startup command or startup Enter. The adapter also requests
foreground return to the earlier application while the expected Ghostty selection
still holds. The request is best effort and uses a checked process identity.

Terminal.app has no equivalent program argument. Its creation-time input clears
ordinary text in the shell's insertion mode and sources a private bootstrap. The bootstrap waits
for its exact tty binding and discards queued input. This uses Terminal's typed
input fallback; it cannot undo a command already submitted with Enter, and a
custom line-kill binding or a prefix/quote key immediately before the text
(Escape or Ctrl-V) can still prevent the startup command from running. A refused
gate stops the bootstrap before the wrapper; zsh can leave its prompt open when
running or suspended jobs prevent it from exiting.

Selection restoration remains best effort and grants no ownership. An iTerm2 tab
creation restores the previous tab without activating an application. A window
creation waits for iTerm2's own activation state before returning the previous
window and application, while the expected selection still holds. The wait is
bounded; an activation after that bound can still take the foreground. WezTerm selects the previous pane
only when its own GUI reports the new pane as focused. A background GUI's stale
focus record grants no authority to restore a tab.

Creation can briefly select a new surface. Keys discarded during that interval
are not replayed. Physical typing, foreground observations and provider round
trips are recorded separately in the [focus acceptance log](../verification/2026-10-03-v0.1.0-focus.md).

## Terminal.app cleanup (#64)

Terminal.app can keep a closed, invisible, zero-tab window in its scripting
list. Restoring that object to the front could show an empty window again on
the next launch. Selection restoration now considers only visible windows.

After a successful close in the same close operation, an invisible, zero-tab
object is accepted as closed. A visible empty window, remaining tab, failed
read, or unrelated later close operation is not accepted by that rule. A
window lookup that races with disappearance is checked against a fresh list;
the lookup error alone does not prove absence. Existing application identity,
surface ownership, and close-intent checks remain in place.

## Ended owners and timeout regression coverage (#69, #68)

On macOS, an internal request wait now reports an owner that has ended after
first recovering any completed result. Keeping an uncertain terminal handle
for cleanup no longer makes that wait continue to its timeout. The diagnostic
preserves the handle, close intent, and pending request claim. Public
`result --wait` behavior and provider completion identity are unchanged.

The Codex queue timeout fixture now waits for its child to start before
expiring its test deadline. It checks that the entire process group ended and
that uncertain-delivery metadata and the exact request claim remain. This is
a test correction; the production queue deadline and transport did not change.

## Verification and remaining limits

The implementation and Terminal.app runtime evidence are recorded in
[the 0.1.0 issue work log](../verification/2026-10-03-v0.1.0-issues.md).
The final source passed 680 serial tests (6 ignored: 5 live tests and one
subprocess fixture), Clippy and format checks. Claude Fable and Codex reviewed the changes. Physical typing,
selection return, Claude initial and follow-up requests, and owned-session
cleanup passed on running iTerm2, Terminal.app, Ghostty and WezTerm applications.
The [focus acceptance log](../verification/2026-10-03-v0.1.0-focus.md) preserves
the failed candidates, final binary identities and component mapping.

- Keyboard focus and keys typed while a surface is being created remain
  separate from provider round-trip and terminal ownership checks (#58).
  Terminal APIs can select or activate newly created surfaces. A restored
  tab does not prove that another application retained the keyboard.
  These checks cover running applications, not cold start, every shell key
  binding, or lossless delivery of every key during creation.
- WezTerm has no atomic screen-check-and-key API, so Bridge does not
  automatically answer workspace trust dialogs there. A shared session has
  no authority to quit its GUI, even after the last pane closes; a GUI may
  therefore remain under keep-open settings.
- Native Windows provider live evidence from 0.0.10 is historical evidence
  for unchanged paths, not new 0.1.0 runtime verification. Claude workspace
  consent and Codex's agent-switch view remain unverified.
- Ignored live tests and cross-platform compilation do not establish
  authenticated provider, physical screen, or keyboard behavior.
