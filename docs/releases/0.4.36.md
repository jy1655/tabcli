# Terminal Agent Bridge 0.4.36

0.4.36 adds a read-only `screen` query for a managed session's terminal (#346) and gives an
unattended child's question a way back to its caller on both providers that have a structured
question tool: Claude's `AskUserQuestion` call is refused before its dialog with a reason that
asks the child to end its turn with the question (#340, #343), and Codex's asynchronous question
is let through with a notice that asks the child not to wait for a reply in its turn (#342,
#351). Both are on by default and each has a setting. Neither forces what the child writes.
Four fixes follow from a re-check of earlier findings (#345, #347, #348, #350). No transport
was added and no command sends input it did not send before.

## Screen query

`tabcli screen <session> [--timeout-secs N] [--json]` returns the visible text of the session's
own bound terminal surface at one moment, so a caller that cannot see the host's terminal can
look at a dialog, an error or an update screen while a request stays pending. It makes the
surface ownership check that `tell` makes, reads the screen once, then reads the binding again
and repeats the check, and returns the text only if the same handle and the same owner record
held before and after the read. It sends no input, key or activation request, writes no record
and classifies nothing. The text is what the terminal showed at one moment, not evidence about
a request, and it can contain secrets the provider printed. Ghostty and Warp are refused: their
scripting interfaces expose no screen text. `describe` gains the effect key `reads_surface`.
See [CLI](../cli.md#screen).

Limits stated in the help: a terminal application that quits between the running check and the
read can be started again by the scripting call; on native Windows a caller without a console
can get a console window from the screen helper (not verified); on macOS a terminal call that
times out is followed by a screen-lock probe of up to 0.5 s.

## Claude question deflection

Nobody is at a managed Claude session's `AskUserQuestion` dialog, so a request that reached it
stayed pending until someone answered at the surface. A Claude session launched with
`settings claude-question-deflection on` (the default) has its question plugin refuse the
model's own main-loop `AskUserQuestion` call before any dialog, with a fixed reason that asks
the child to end its turn with `QUESTION FOR CALLER: <question> Options: <option labels>`. When
the child does, the turn completes as an ordinary Result, the emission record still holds the
structured question, and the caller answers with an ordinary `tell`. When the refusal is
attributed to the request's turn and recorded, outputs that report question presence add
`question_deflected: true` and `question_deflection_count`, and the refused item in
`question_emissions` carries `deflected: true`. `inspect --json` reports
`capabilities.questions.response` as `deflected_to_result` for such a launch, which is what was
configured.

The flags are evidence that a call was refused, not that the Result is a question: read the
Result before treating the request as finished. A refusal that cannot be recorded leaves no
flag, and when the plugin is not loaded or its hook fails the call reaches the dialog as before.

A settings `PreToolUse` hook of your own for `AskUserQuestion` does not run for a call the
plugin refuses; `settings claude-question-deflection off` keeps such a hook and the dialog for
sessions launched afterwards. Subagent questions, a plugin's own questions and calls the plugin
did not observe reach the dialog as before. See [CLI](../cli.md#question-deflection).

## Codex question notice

Codex's `request_user_input_async` returns at once and leaves the turn running. Measured on
codex-cli 0.166.0: a child with nothing else to do kept its turn open waiting for a reply, its
request stayed pending, `tell` was refused, and a message queued with `codex queue` waited for
the turn to end instead of joining it
([measurement](../verification/2026-11-05-macos-342-codex-question-answer.md)).

A Codex session launched with `settings codex-question-notice on` (the default), with lifecycle
hooks injected and a recorded Codex version of 0.166.0 or newer, carries one more `PreToolUse`
hook that runs for that tool only. It refuses nothing: the question is asynchronous by design
and the child may keep working while it is open. The hook adds a notice for the model that no
reply can arrive during the turn, that it should finish the work that does not depend on the
answer, and that it should end its turn with the `QUESTION FOR CALLER:` line. The question is
still emitted and recorded as before, and the caller answers with an ordinary `tell` once the
request has ended. `inspect --json` reports `capabilities.questions.response` as
`answer_after_turn` for such a launch. The decision is recorded per session at launch, and
`doctor --probe` checks the added hook's trust hash against the installed Codex.

The notice is advice to the model: a child that ignores it can still wait in its turn, and then
the request stays pending as before. A trust hash that a later Codex no longer accepts would
hold its hook-review picker before the initial prompt, as for the two lifecycle hooks;
`settings codex-question-notice off` launches later sessions without the hook. See
[CLI](../cli.md#question-notice).

## Fixes

- A launch whose trust-dialog answer failed left its request claimed: for a provider whose
  initial prompt Bridge delivers after launch (Claude, and Agy on native Windows) `result`
  stayed `pending` and `tell` was refused. Such a launch now ends as a recorded delivery refusal
  when the session is still awaiting its initial input (#348).
- `inspect --timeline` names every receipt the request index refuses, with the reason, not only
  receipts whose bytes fail to parse (#347).
- The Codex doctor's notify-payload budget check reads the pending receipt through the shared
  decoder, and Claude's native pending record is frame-checked by the delegation header
  constant (#345).
- `screen` on a Ghostty session says that Ghostty's scripting dictionary exposes no screen text
  instead of reusing the guarded-input message (#350).
- The Claude module test harness passes its input as a file descriptor and bounds every call,
  after a `spawnSync` stdin stall was reproduced on macOS; the serial test steps of CI and
  Release have explicit timeouts (#344). No product code changed.

## Verification and upgrade

Before the version bump, the complete local Rust suite passed on macOS (1,659 passed, 6
ignored) and the Python script suite passed (109 run, 2 skipped). Live checks on one Mac with
iTerm2, codex-cli 0.166.0 and Claude Code 2.1.318 are recorded for the
[screen query](../verification/2026-11-05-macos-screen-query.md), the
[Claude question deflection](../verification/2026-11-05-macos-340-claude-question-deflection.md)
and the [Codex question notice](../verification/2026-11-05-macos-342-codex-question-notice.md).
None of the three was run on native Windows, and the Windows trust-hash vector of the notice
hook is computed only: no Codex on Windows has reported it. The live checks used development
builds. The packaged 0.4.36 release's runtime and authenticated provider round trips with it
are not verified by these notes; those checks are separate and recorded outside this repository.

After the upgrade, new managed Claude sessions have the model's own `AskUserQuestion` calls
refused before their dialog, and new managed Codex sessions on 0.166.0 or newer carry the
notice hook; each setting restores the earlier behavior for sessions launched afterwards. A
session launched by an earlier binary keeps its launch decision and has neither. If Codex launches stop at a hook-review picker after a
Codex update, `tabcli doctor --provider codex --probe` reports each injected hook's trust
status, and `settings codex-question-notice off` launches without the added hook.

The [open-session upgrade notes](0.4.25.md#upgrade-notes) still apply. Do not downgrade a
binary used by an open session. The release includes macOS and Windows CLI archives and
Claude, Codex, Agy and Pi integration packages with checksums. Integration packages contain
instructions, not the engine binary; updating an integration takes effect in new host
conversations.
