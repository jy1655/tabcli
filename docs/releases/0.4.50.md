# TAB 0.4.50

0.4.50 makes several behaviors the same on macOS, Linux and Windows: the automatic terminal
choice inside an hc terminal, the refusal of a terminal the operating system does not run, and
the close of a Herdr terminal whose owner is gone. A verified git worktree can now inherit its
repository's workspace consent, and Agy 1.5.17 or newer receives a consented workspace for one
session instead of showing its trust dialog. Two launch failures that surfaced as a timeout can
end early with their reason. Commands and JSON output keep their form; consent records gain
one optional field and two marker values.

Each item names its pull request, whose description has the conditions and limits in full.

## What changes for a caller

- **Automatic terminal inside an hc terminal (#413, #420):** every OS chooses the same way.
  TAB uses Herdr when the provider, at its installed version, can run there, and otherwise the
  terminal that OS uses outside Herdr: Ghostty on macOS, tmux on Linux, the managed console on
  Windows.
  - A Codex that passes the general version check (0.147.0 or newer, readable) but not
    Herdr's (stable 0.169.0 or newer) was refused by an automatic `ask` on macOS and Linux in
    0.4.49. It now starts in the fallback terminal, whatever the Herdr caller check said. TAB
    does not check that the fallback terminal is installed before the session exists. On
    Windows, where Codex cannot run on Herdr, every Codex the general check accepts takes
    the managed console, as in 0.4.49.
  - When the choice falls back, the session's `launch.log` gets one best-effort line with
    the reason, on every OS.
  - An explicit `--terminal herdr` that cannot be admitted is still refused.
  - `doctor --provider <provider> --probe` reports the terminal `ask` would choose and its
    fallback. It does not make the caller check, and when the version probe that decides
    fails, it reports no terminal, with the fallback and what Herdr requires.
  - On Windows an automatic `reopen` of a closed Claude session now makes the Herdr caller
    check and uses Herdr.
- **Reading the Codex version for Herdr (#413):** output with the `codex-cli` label is read as
  in 0.4.49. In output without the label, TAB counts the words that contain three
  dot-separated numbers. Exactly one such word is read, after enclosing punctuation and one
  leading `v` are removed, and must then parse whole as a version: `OpenAI Codex (v0.170.0)`,
  which 0.4.49 refused, is read again. A second such word, for example an address, makes the
  output unreadable for Herdr. When the general version check accepted such output, an
  automatic choice takes its fallback and an explicit `--terminal herdr` is refused; output
  the general check cannot read is refused by that check, as before.
- **Launch failures that can end early (#416):** a launch host refuses a session directory
  that is not private to its user; in 0.4.49 that refusal went to `launch.log` only and `ask`
  waited for the launch deadline.
  - TAB now makes that check itself before any terminal exists and fails with the reason
    when it observes a violation: for Herdr with the core's account, for tmux with its own,
    for the macOS terminal applications without an account. The managed Windows console has
    no such check. When TAB cannot read what it needs, the host decides as before.
  - A session directory whose path is not Unicode text is now refused for every host that
    receives the path as text.
  - A Herdr terminal that its core reports finished before startup was confirmed ends the
    wait at the next probe, when TAB establishes under the session's lock that it is the
    terminal of this still-pending launch. Otherwise the wait continues as before.
- **Workspace consent in a git worktree (#417):** when no provider trusts the workspace
  exactly, a linked git worktree that Git verifiably registers under a main working tree can
  inherit that main working tree's consent in TAB. #417 has the conditions in full; among
  them:
  - The provider that supplied that consent must neither decline nor fail to read the
    worktree, and the provider being launched must neither decline nor fail to read either
    tree.
  - Codex and Pi then receive their existing process-local trust options in the worktree.
  - `tabcli consent revoke` or `consent reset` on the main working tree withdraws the
    inherited consent; after a reset, a new `ask` can acquire it again. A running session's
    recheck acquires nothing new.
  - Inherited consent never answers a trust dialog.
  - A worktree registered under another spelling of its path, including one that differs
    only in case, inherits nothing until
    `git -c core.ignorecase=false worktree repair <worktree>` rewrites the registration.
- **Agy without the trust dialog (#417):** for a consented launch of an Agy identified as
  1.5.17 or newer, TAB passes the exact workspace through Agy's session-only `--settings`
  option. No key is sent and Agy's trust store is not written.
  - This also serves exact consent from another provider, where 0.4.49 answered the dialog
    with a guarded key in iTerm2, Terminal.app and the native Windows console and failed the
    launch elsewhere.
  - An Agy identified as older keeps the guarded dialog answer for exact consent, provided
    TAB recorded for that launch that the option is unavailable; without that record no key
    is sent. An Agy whose version TAB cannot identify gets neither
    the setting nor a key.
  - Every paste into Agy needs two facts: that process's own workspace-load line in
    `agy.log`, and either Agy's own exact trust entry or the session-only setting with
    consent that still holds at that moment. After a revoke or reset, a session that relies
    on the setting has its later pastes refused. Native Windows follow-ups now wait for
    these facts as well.
- **A check when the provider starts (#417):** a Codex, Pi or Agy command that carries a
  trust option is checked again just before the provider starts. The provider is not started
  when consent no longer holds, when the grant no longer matches the command's provider,
  workspace and option, when the planned path no longer yields a private settings file with
  the planned bytes, or when the check cannot finish within the launch's remaining time.
- **A terminal the OS does not run (#414):**
  - `--terminal` with such a kind is refused before a session exists, with
    `<Name> is not available on <OS>; use <the kinds that OS runs>`. macOS used to create the
    session and fail when it opened the terminal.
  - A stored handle of such a terminal is refused with the same text at the adapter lookup on
    every OS. A kind's own declared screen or guarded-input refusal still answers first, and
    the `screen` command answers from the records with
    `the recorded terminal, <Name>, is not supported on this platform`.
  - On Windows such a handle used to reach the managed console adapter. A send to it is now
    known not sent, its ownership check refuses, and `doctor --probe` reports the surface as
    unverified; 0.4.49 could report an uncertain delivery or a missing surface.
  - A handle that belongs to another session is reported as unbound before its kind is
    judged, and guarded input is refused before the Claim is checked.
  - A `close-session --explicit` that still has to act on such a terminal is refused and
    keeps the handle, also on a second attempt. A close that an earlier, interrupted close
    already recorded as consumed finishes from the records. The session can be closed on the
    system that created it.
- **Closing a Herdr terminal whose owner is gone (#415):** the rule is now the same on every
  OS. When no live owner of the session is verified, `close-session --explicit` never ends a
  running Herdr terminal. It removes a finished terminal that the verified core identifies as
  the one the session created and that is not set to keep, settles the session when that core
  reports the recorded terminal as not found, and refuses a running one, naming the commands
  to inspect and end it on the recorded core. Dead-owner Repair leaves a Herdr terminal for
  that close. The points below describe a session without a saved teardown intent; the last
  one covers a saved intent.
  - No longer ended: in 0.4.49 Windows Repair ended a running terminal of a gone owner; on
    every OS an explicit close ended one after a failed start or before the wrapper had
    recorded its owner; on macOS and Linux so did a resumed close whose owner had gone.
  - Now closable: a finished or absent terminal closes whatever the owner record says.
    0.4.49's ordinary close on macOS and Linux refused it for any owner record other than a
    complete, bound record of an exited owner; on Windows an owner record or process that
    could not be read made the close refuse; on every OS a session without an owner record
    was refused outside `launching` and `failed`.
  - Stricter: on Windows a finished terminal is removed only when its launch label matches
    the handle's, as on macOS and Linux. On every OS a handle whose recorded host PID, host
    birth or launch label is a value no released TAB version writes is refused before the
    core is asked. Without a verified live owner, the cleanup after a refused `reopen`
    leaves the terminal and its handle for `close-session --explicit`.
  - The closed record keeps the session's stored error on every OS; 0.4.49's explicit close
    on macOS and Linux dropped it. Without a stored error, an owner the OS reports gone adds
    `native session process <pid> is no longer running`.
  - On Windows an attached `ask` or `tell` now stops waiting once the recorded owner is
    verified gone, as on macOS and Linux.
  - Other terminal kinds keep their platform's rule.
  - A session with a saved teardown intent (macOS and Linux) still replays under 0.4.49's
    rules. While the intent does not validate, for example because the owner record is
    gone, the close refuses even a finished or absent terminal. A validated replay that
    leaves the close to the surface alone now refuses a running terminal, which 0.4.49
    ended; #415 has its finished and absent cases.
- **Fixes (#418):** on macOS, a reply that a Herdr core sent before it closed its socket is no
  longer lost and reported as unanswered. On Linux, a `/proc/<pid>/stat` entry read after the
  task's signal state was released no longer makes a repeated tmux close fail with
  `invalid digit found in string`: on such an entry the tmux server check asks its pidfd. A
  reported exit proves the server gone; otherwise the birth is read once more, and a second
  such entry refuses.
- **Documents (#432):** the security page states what the permission checks on local records
  and trust stores examine and what they do not. No behavior changes.

## Verification and upgrade

- Tests: on the release source the serial suite passed on macOS 27.2.1 with Rust 1.98.1
  (2,252 tests, 6 ignored), with fmt, Clippy with `-D warnings` on the host and for the
  Windows and Linux targets, and the build check for an operating system without a terminal
  transport. CI ran the suite on main before the version change (`fcfdf3a`) on macOS (2,252
  tests), Linux (1,868) and Windows (1,914), and passed on each pull request.
- Live, on macOS only (record in
  [the 2026-11-27 verification](../verification/2026-11-27-0.4.50.md)):
  - With a build of the release source: Codex, Claude and Agy round trips on Herdr, the Agy
    session with the session-only setting; the refusal of `--terminal tmux` and
    `--terminal windows-console` before a session exists; and an explicit close after a
    Herdr session's owner was ended outside TAB, which removed the finished terminal and
    closed the session.
  - With a build of the head of #417, and Agy 1.5.18: a new git worktree inherited consent
    and started without a trust dialog, and an empty folder without consent showed the
    dialog.
- Not run live: Linux and Windows; Pi; every terminal other than Herdr; the fallback from
  Herdr with an old Codex and its launch-log line; the launch failures of #416; a stored
  handle of a terminal the OS does not run; a running Herdr terminal without a live owner;
  consent withdrawn between planning and the provider's start or a paste; an Agy older than
  1.5.17. They are covered by tests only.
- Upgrade:
  - Consent records gain the optional `repository_root`; records without it keep their
    earlier shape. The `applied` field of a session's `workspace-consent.json` takes two new
    values, `agy-settings-override` and `launch-option-unavailable`; a marker alone proves
    neither consent nor a launch. An `ask` in a worktree can write the main working tree's
    shared record. A session directory can hold `workspace-consent.lock` and
    `agy-session-trust-<random>.json` files until `prune-sessions` removes it.
  - On Windows the consumption marker now carries the close's `reason`, as on macOS and
    Linux, and a marker that already records `consumed: true` is kept as written. No other
    Record changes.
  - After a rollback to 0.4.49: it does not grant inherited consent, and its
    `consent revoke` of an inherited record drops `repository_root`, which leaves the record
    revoked after a later upgrade until `consent reset`. It withholds follow-ups to an
    Agy session that relied on the setting on macOS and Linux unless Agy's own store lists
    the workspace, and pastes them without a trust check on native Windows. It handles a
    Herdr session that this build left open under its own rules; on Windows its Repair ends
    a running terminal. Its Windows replay of a consumption marker ignores the `reason` and
    rewrites the marker.
  - Continuing a running session across the upgrade, and a rollback, were not exercised
    live.
