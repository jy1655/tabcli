# Terminal Agent Bridge 0.4.25

0.4.25 settles Claude requests from Claude's official turn lifecycle instead of the first Stop
hook, on native Windows (#283) and macOS (#301, closes #249): a Stop hook that blocks the stop and
continues the turn no longer publishes the draft. Every platform now requires stable Claude Code
2.1.302 or newer. The release also keeps Codex completion observable after a tool output larger
than 8 MiB (#297, closes #269), requires a typed owner death before launch repair (#282) and
before failed-start close authority (#300, closes #299), concentrates the Terminal.app incarnation
checks with no behaviour change (#298), and publishes the host integration metadata in English
with a language lint in CI (#296).

## Upgrade notes

- Claude Code below 2.1.302, or a prerelease, is refused before launch on every platform; public
  preflight, `doctor` and help agree on this floor (#301). Codex, Agy and Pi keep their minimums.
- Claude sessions opened by an earlier binary use the legacy Stop completion. A pending request in
  such a session can still finish and remains readable after the upgrade, but a new `tell` into it
  is refused on both platforms. Inspect the result and the terminal and close the session when
  appropriate; then start a fresh `ask` with the context you need on macOS, or `reopen` on native
  Windows to get native completion.
- Do not downgrade the binary or `AGENT_BRIDGE_EXECUTABLE` while a Claude session opened by
  0.4.25 is open: older binaries cannot interpret its completion protocol.

## Observable changes

- Claude native completion (#283 on native Windows, #301 on macOS). New launches, and Windows
  reopens, load a session-local Bridge completion module through Claude's official `--plugin-dir`
  flag and wait for the module's actual readiness before sending anything. The initial prompt and
  every follow-up go through Claude's official cross-session messaging; argv carries no prompt.
  Hooks disabled with `disableAllHooks: true`, unresolved plugin trust or provider policy can
  withhold readiness: Bridge then sends nothing and substitutes neither a Stop hook nor terminal
  input. The module forwards Claude's main-loop `turn.start` and `turn.complete`; Bridge binds the
  complete addressed prompt to the current request at `turn.start` and publishes only from the
  official completion. A classic Stop or StopFailure never settles such a request, so a Stop hook
  that continues the turn, including your own, no longer produces a draft result.
- Marked completion and background continuation (#283). A normal answer completes the request only
  when it ends with the exact delegation marker, which Bridge strips. A nonempty answer without the
  marker, such as the interim that ends a turn while background work continues, is kept as a
  candidate: it neither releases the request nor becomes a result. A later main-loop completion in
  the same conversation finishes it only with a valid nonempty answer ending in the exact marker;
  that result has `claude_mod_marked_continuation` provenance, and both official turn ids stay in
  private records. This is a marker protocol, not provider-owned parentage: an unrelated turn that
  repeats the marker can match, a marked interim can finish early, and a genuine final without the
  marker stays pending, also after a caller timeout. `tabcli inspect <session>` shows that state
  and its candidate without retrying, repairing or publishing anything. An official interrupted,
  API-error, refused or empty final fails the bound request; malformed or unmatched signals keep
  the request pending and write the latest reason to `claude-mod-diagnostic.json`. Native
  completion messages are limited to 4 MiB of UTF-8 JSON, and an oversized bound answer fails
  without truncation. `cancel` remains unsupported for Claude.
- Codex completion after oversized tool output (#297, closes #269). A single transcript record
  over 8 MiB, such as a tool output carrying several images, previously suspended the bound request
  so that its answer was never published. The observer now reduces such a record in place: it
  validates the whole line as strict UTF-8, replaces every string over 4 KiB with an empty string
  after validating it, and requires the reduced record to parse as JSON within 8 MiB. It skips the record only when it is a
  non-message `response_item` after the verified session identity with intact, unrepeated
  discriminators, so the request can reach its own terminal record. Any other record over 8 MiB,
  including a user message with pasted images or a terminal record, still suspends observation as
  `oversized`. Each poll still reads at most 256 KiB, so a large record can delay the result.
- Launch repair (#282). Startup repair marks an unconfirmed launch failed only when the typed owner
  attestation reports the recorded owner gone (exited or pid reused). A live owner whose control
  identity changed stays live, and an unknown or unreadable owner returns an error without changing
  the session status or releasing the request; the launch deadline still fails startup on its own.
- Failed-start close authority (#300, closes #299). Closing a session whose start failed could
  treat a live owner with changed control identity, or an unknown owner with a false liveness
  diagnostic, as dead and close its iTerm2, Ghostty or Windows console surface on that basis. The
  shortcut now requires the typed attestation's verified exit or pid reuse; other owners go through
  the later ownership checks as before.
- English integration metadata and language lint (#296). The host integration packages and their
  marketplace catalogs use English names, descriptions and suggested prompts, and both READMEs give
  per-host installation and invocation commands. `scripts/check_language.py` runs in the Linux,
  macOS and Windows CI jobs and rejects non-ASCII letters outside documented exceptions.

## Module moves (no behaviour change)

- Terminal.app incarnation (#298). `apple_terminal/incarnation.rs` owns ancestry capture, the
  live and unique decisions, the close transaction bracket and the separate absence-observation
  order; every close and retry keeps its deadline, birth and uniqueness checks in the same order,
  and scripts, errors and runtime literal pins are unchanged.

## Verification and limits

Each change passed the serial suite (`cargo test --all-targets --all-features --
--test-threads=1`), Clippy with `-D warnings` on the host and for Linux GNU and Windows MSVC, fmt,
the language lint and `git diff --check`, and all seven jobs of its own CI before merge. One
main-push run failed without a code defect: for #296 (run 39902489107) the macOS job could not
resolve `index.crates.io` while fetching dependencies for Clippy, and the Windows job was cancelled
in that step; the next main push, which contains #296 (run 39907754189), and every later main push
passed. Final main `6a04002` passed all seven jobs (run 39936304199).
