# Terminal Agent Bridge 0.4.22

0.4.22 records a delivery that Bridge refuses before sending as the request's failed result,
so that a refused follow-up no longer leaves the session's delivery outcome uncertain and no
longer blocks the `reopen` that the refusal itself recommends (#268). It also requires local
build cleanup at the end of every release (#267).

## Changes

- Delivery refusal settlement (#268). A `tell` or initial delivery that Bridge refuses before
  anything is sent (preparation, budget, hold or transport refusal) previously rolled back the
  claim and kept the reason only in the mutable `status.error`; the request's receipt had no
  event, `result` reported it as `unresolved`, and `reopen` refused the closed session with
  `request-unresolved`. The second regression of PR #260's Windows verification was this: a
  follow-up into a legacy Windows session was refused with "close and reopen it", and the reopen
  then failed on that very request. The refusal is now journaled as the receipt's failed event
  under the lifecycle lock that settlement already holds: a pending provider completion is
  recovered first and wins, the installed claim must be the settling token, a closed session is
  left alone, and the event carries the refusal text, `provenance: delivery_not_sent`, the
  provider from the manifest, no provider session or turn id, and `created_unix_ms`. A failed
  journal write leaves the claim installed. Every query shows the request as `failed` with the
  refusal; `inspect --timeline` marks it `stage: delivery_refusal`, `delivery: refused_not_sent`;
  `search` skips it as an error event; `reopen` accepts the session and keeps an older event's
  provider identity. The native Windows queue follow-up refused above the command-line limit
  (#251) therefore reads `failed` instead of `unresolved`.
- The settlement is prospective. A receipt that an earlier binary left without an event stays
  `unresolved`; nothing is inferred from `status.error`, and no query repairs it. The follow-up
  refusal of a reopened conversation in `reopen.rs` still leaves an unresolved receipt on purpose.
- Local build cleanup (#267). `docs/releasing.md#local-build-cleanup` and the project
  instructions require a full `cargo clean` of this checkout's `target/` after publication
  verification, installation and all checks, with the dependency checks that precede it. The
  command pins both the final and the intermediate build directory to `./target`, so a
  separately configured `build.build-dir`, other worktrees, installed binaries, session
  records and global Cargo caches are left intact.

## Verification and limits

The PR #268 branch validation reported a passing serial suite (`cargo test --all-targets
--all-features -- --test-threads=1`: 1,202 passed, 2 ignored in the library, plus the doc and
integration binaries), host Clippy with `-D warnings`, Linux and Windows cross-target Clippy, fmt
and diff check, and the release preparation repeated the same gates on this version. Main-push
CI run 39722351843 for the merged commit `162b3958ad26a600f3712f5281e9cfcb06509e6e` succeeded
on every job, including the Windows runner. The new tests
went red on the previous behavior (empty events, `unresolved`, claim released after an injected
journal fault, reopen refusing) before the change. Tests that pinned "no event on NotSent" were
changed deliberately, each with a comment. No production provider adapter source changed; one Codex paste-test fixture was updated. A Codex critique
of the disposition preceded the implementation and a Codex review of the branch found no
blocking defect.

Not verified: the #260 Windows scenario itself. Claiming it fixed needs a fresh legacy Windows
source session and a refusal settled by this binary, which this release does not include. No
authenticated live provider run was part of this release; the installing machine's self-test
is recorded separately. The first regression of PR #260 (a Claude background-task turn whose
unmarked interim answer is published as the completion, #249) is not addressed here.
