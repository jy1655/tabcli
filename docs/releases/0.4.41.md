# Terminal Agent Bridge 0.4.41

0.4.41 keeps a shell startup file that waits for terminal input from holding an iTerm2 or
WezTerm launch, fails a launch whose shell environment cannot be prepared as soon as that is
known and names the stage, and adds `doctor` checks for both (#376, #377).

## What changes for a caller

- **iTerm2 and WezTerm launches (#376):** the new surface now runs Bridge's host directly. The
  host runs your zsh login and interactive startup files once without a terminal
  (`/bin/zsh -l -i`, no controlling terminal, standard input from `/dev/null`), for at most ten
  seconds and within the launch deadline, keeps the exported environment that run produces, and
  starts the launch with `/bin/zsh -f -i` in the surface and that environment. Before, the
  surface ran `/bin/zsh -l -i -c` on its terminal, so a startup file waiting for input (Oh My
  Zsh's update prompt, every 13 days by default) held the launch until
  `provider launch timed out before startup was confirmed`, and nothing in the session's
  records showed why.
  - Exports that a startup file makes only when attached to a terminal (under `[[ -t 0 ]]` or
    after `tty`) are no longer carried, and neither are shell functions, options or limits. As
    before, zsh does not pass on a variable whose name is not a shell identifier.
  - Startup-file output is discarded; it is never stored, logged or shown.
  - Processes a startup file leaves in that run's process group are stopped and counted, and
    the launch continues. A daemon that detaches itself is not touched.
  - Keys typed into the new surface while the environment is prepared are discarded before the
    launch shell starts.
- **A launch whose host records a failure:** while the launch is still pending, a failure that
  the host recorded for it fails the launch without waiting for its deadline. A host that exits
  without recording one may leave the launch waiting until its deadline. A run of the startup
  files that does not finish, exits with an error or produces no usable environment reads, for
  example, `terminal shell environment could not be prepared: startup files did not finish
  within 10000 ms (capture_timeout); last recorded launch stage: environment_preparing`. Other
  host failures read `terminal launch host failed: <reason> at <stage> (<reason>); last recorded
  launch stage: <stage>`. A launch that still reaches its deadline keeps the existing text and
  adds `; last recorded launch stage: <stage>` when a readable host record of that launch
  exists; otherwise, as for a session launched by an earlier release, the text is exactly the
  earlier one.
- **`doctor SESSION`:** a new `launch_stage` check reports the last stage the launch host
  recorded (`awaiting_host`, `host_started`, `environment_preparing`, `environment_ready`,
  `launch_shell_starting`) and, when it failed, the reason. When no host record exists, another
  terminal, or a platform other than macOS, is reported as not applicable. An iTerm2 or WezTerm
  session without that record, or one whose terminal is unknown (an earlier release, or a launch
  that did not reach surface creation), is reported as not recorded, never as a host that did
  not start; for such a launch that timed out with no `wrapper_started` in its launch log, the
  next action names a startup file waiting for terminal input as a known cause. A closed
  session's terminal kind is read from its close record.
- **`doctor --probe`:** on macOS for iTerm2 or WezTerm, a new `shell_environment` check runs the
  same preparation once in the caller's current environment, within the shared five-second probe
  budget, and reports only the outcome, elapsed and budget milliseconds, the variable count,
  stopped processes and a numeric exit status or signal. A timeout within a budget shorter than
  the launch's ten seconds is reported as inconclusive. The probe runs your startup files, which
  can have side effects. Without `--probe`, or for another platform or terminal, the check says
  so and runs nothing.
- **`inspect --timeline`:** a `launch_host` entry shows the host record; a present record that
  cannot be read or belongs to another launch is shown as unreadable and marks the timeline
  incomplete.
- **`scripts/share_diagnostics.py`** accepts the new check ids and reasons; it still drops
  details and evidence.

Terminal.app, Ghostty and Warp are unchanged: Terminal.app and Warp type the launch into the
terminal's own shell, and Ghostty already starts a clean shell with the launcher's `PATH`.

## Tests

- Tests that located the package binary two directories above the test binary now search
  upward, because Cargo 1.100 (Rust 1.100.0, 2026-11-12) moved unit-test binaries under
  `target/<profile>/build/<package>/<hash>/out`. This changes no shipped code.

## Verification and upgrade

- Local on the release change (Rust 1.99.1): the serial test suite (1823 passed, 0 failed, 6
  ignored), Clippy with `-D warnings` on the host and for `x86_64-unknown-linux-gnu` and
  `x86_64-pc-windows-msvc`, fmt, the language lint, the scripts tests (109 run, 2 skipped) and
  the integration check. The #377 branch also passed the serial suite on Rust 1.100.0 (1823
  passed, 0 failed).
- CI: #377 passed all seven jobs on its final head (the Rust job on Linux, macOS and Windows,
  MSRV, both release builds and the integration packages).
- Regression: a pseudo-terminal test runs the production-generated iTerm2 command (through
  Bridge's test model of iTerm2's argument parser) and the WezTerm program vector with fixture startup files whose
  `.zshrc` reads one key from the terminal. The 0.4.40 bootstrap never reaches the host there;
  0.4.41 does, and keys typed during the preparation are discarded.
- Live, on one Mac with codex-cli 0.169.0 and a temporary `~/.zshrc` line that reads a key only
  when attached to a terminal: 0.4.40 timed out in iTerm2 with no `wrapper_started`, as
  reported in #376; a build of #377 before its final review fixes (which touched only `doctor`,
  the timeline and tests) passed `self-test codex` in iTerm2 and WezTerm, preparing the
  environment in about 1.5 seconds, and `doctor --probe` reported the recorded stage and a ready
  preparation.
- Not run live: native Windows and Linux (CI only; neither uses this bootstrap), Terminal.app,
  Ghostty and Warp, startup files that start daemons, and a raised `RLIMIT_NOFILE`, under which
  the descriptor-closing loops of the capture take longer.
- A new private record, `launch-host.json`, is added to iTerm2 and WezTerm sessions; no existing
  record schema changed. As before, do not downgrade the binary while sessions it opened are
  still open.
