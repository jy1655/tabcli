# Agent Bridge 0.0.5

Agent Bridge 0.0.5 fixes Claude follow-up (`tell`) deliveries that failed with `could not confirm delivery` and left the session `working` until it was explicitly closed, although nothing had reached the target session.

## Highlights

- In 0.0.4, the messenger had to copy the whole follow-up message into the `SendMessage` input. With Claude Code 2.1.276 through 2.1.278, the provider could stop that response part-way or refuse the messenger input, so the call never ran. Agent Bridge saw a `SendMessage` call in the messenger output, reported `Claude SendMessage call changed the addressed payload`, classified the attempt as delivery-uncertain, and kept the turn claimed.
- The follow-up message no longer passes through the messenger model. The messenger presents only a short per-request reference. The guard verifies recipient, summary and reference, and supplies the exact follow-up message as the executed tool input through the official hook output `updatedInput`. The guard approves at most one call per request and writes the approval record before the approval takes effect.
- A temporary `PostToolUse` hook writes a receipt from Claude's report of the input that actually ran. Delivery is confirmed only when three things agree: the messenger output stream (one discovery and one successful `SendMessage` call that presented the reference), the approval record, and a verified receipt.
- An unconfirmed attempt is retried only when it provably never ran: there is no approval record and no receipt, and either the stream contains no `SendMessage` call at all, or Claude itself reported every `SendMessage` call in the stream as blocked before it ran. A blocked-call report is an error result whose complete text is exactly the guard's denial reason, or exactly Claude's result for a call in a response that the provider stopped. Retries stay inside the existing 5-second window and the total `tell` timeout.
- A `tell` that still cannot send releases the turn claim and returns the session to `ready`, so the same session accepts another `tell`.
- An error result, a missing approval record, and the guard's own decision are not proof that nothing was sent: `SendMessage` is not permission-gated, and Claude discards the output of a hook that outlives its timeout and then runs the call unguarded. Every other unconfirmed attempt stays delivery-uncertain and keeps the turn claimed, which prevents a duplicate delivery.
- When a follow-up stays claimed as delivery-uncertain, the reason is now written to the `error` field of the session's `status.json`, and only while that turn still owns the turn claim. A stuck turn is therefore distinguishable from ordinary `working`.
- The messenger's temporary files (hook settings, expected follow-up message, approval record, receipt) are created per request, because the target can finish a delivered turn, and the next `tell` can start, before the previous sender has finished cleaning up.
- The Codex, Agy and Pi adapters are unchanged.

## Requirements

- Rust 1.97.1 or newer when installing from source.
- PowerShell 7 for native Windows managed consoles, regardless of the caller shell.
- Provider CLIs installed, authenticated, and initialized before Agent Bridge launches them.

Minimum provider versions remain Codex 0.147.0, Claude Code 2.1.234, Agy 1.1.12, and Pi 0.84.1.

## Verification boundary

- A deterministic regression test reproduces the stream of a provider-stopped call; it failed on the 0.0.4 classification before the fix.
- The release candidate passes 187 unit tests and 15 policy tests with `cargo test -- --test-threads=1`; host, Windows GNU and Linux GNU cross-target Clippy with warnings denied; formatting; and diff checks. The four ignored authenticated tests remain manual by design.
- On the loaded development Mac used for this release, the default parallel `cargo test` fails two Codex adapter tests with 0.5–1 second deadlines; they fail identically on unmodified 0.0.4 sources and pass single-threaded. The Codex adapter was not changed.
- Authenticated macOS LIVE with Claude Code 2.1.278 and iTerm2: the installed 0.0.4 reproduced the failure (1 of 1 `tell` failed and stayed `working`). The fixed build delivered 20 of 20 `tell` requests — short prompts, a 5.5 KB prose prompt and hostile text, attached and with `--detach` — byte-exact in the target transcript, with correlated turn IDs and no messenger files left behind. Three of those went to a session that 0.0.4 had launched.
- A wrong reference sent through the real hooks was reported by Claude as an error result carrying the guard's denial reason, with no approval record, no receipt, and nothing delivered to the target.
- The final classifier was also run once against the real captured Claude Code 2.1.278 streams: the provider-stopped call and the guard-denied call counted as blocked; delivered and unguarded-success streams did not.
- An independent Codex review ended with approval after four rounds. The reviewer repeated the single-threaded tests, host Clippy, formatting and diff checks, and did not repeat the LIVE runs.
- `NOT-VERIFIED`: native Windows runtime for this change (the Windows initial prompt uses the same messenger), Terminal.app for this change, and a provider-stopped call under the new design, which cannot be induced on demand and is covered by the captured streams and deterministic tests.
- Release publication requires the repository immutable-releases setting, an `IMMUTABLE_RELEASES_READ_TOKEN` with repository `Administration: read`, and an annotated `v0.0.5` tag whose commit is contained in `main`. The tag, Cargo version, release notes, packaged binary version, archive manifest, and checksum must agree.

## Known boundaries

- The recognized provider-stopped result is the exact text observed with Claude Code 2.1.278. If the provider changes that wording, such an attempt is treated as delivery-uncertain and keeps the turn claimed instead of being retried.
- A messenger attempt ended by the `tell` timeout remains delivery-uncertain.
- A delivery-uncertain turn is released when the target reports completion or when the session is closed with `close-session --explicit`.
- Each `tell` to a Claude session still needs one separate Claude transport turn.
- Boundaries stated for 0.0.4 are unchanged: Linux visible-terminal transport is not implemented, Agent Bridge controls only terminal surfaces that it creates, and Ghostty remains fail-closed.
