# Terminal Agent Bridge 0.4.40

0.4.40 answers one more form of Claude's workspace trust dialog, names a provider version change
when a session's first request is not delivered, refuses a linked `events` path in every listing,
and bounds the launch wrapper's provider version re-check. Five internal reorganisations change
no behaviour.

## What changes for a caller

- **Claude with `--yolo`, in a folder whose `.claude/settings.local.json` pre-approves tool
  permissions (#367):** Claude Code 2.1.322 adds a paragraph to its workspace trust dialog there
  ("This folder pre-approves 2 tool permissions ..."). Bridge now answers that form once, under
  the same consent rule as the plain dialog, and only in the form that was observed: exactly two
  listed permissions in that file. Without `--yolo` the form stays unanswered, because "Yes"
  there also accepts the pre-approvals; the launch then fails at its deadline with the readiness
  error.
- **An initial prompt that was not delivered (#367):** when the provider version of the failing
  session differs from that of the newest other session of the same provider that completed a
  request on the state root, the error names both versions and the `tabcli screen <session>`
  command. It states the versions, never a cause. The read is bounded (the caller waits at most
  5 seconds) and adds nothing when it cannot read the history or the versions are the same.
- **A session whose `events` path is a link, not a directory, or unreadable (#372):** every
  listing of events now refuses it with the existing error (`events directory is a symlink`,
  `events is not a directory`, `events directory is unreadable: ...`). Before, only some
  commands did, and the others read through a link or saw "no events". A completion could never
  be published behind such a path, so what changes is what happened before that point:
  - `tell` fails before delivery and releases its Claim, where it delivered a follow-up whose
    result could never be published. Each refused `tell` leaves its Receipt without an event.
  - `result`, `inspect` and `wait` fail for that session, and `status` marks it incomplete,
    where they reported events from behind the link.
  - `--context-result` refuses to attach a Result from that session.
  - `sessions` shows `"results": 0` for it.
  - A provider's first report of a session and a report that carries a turn id stop before
    anything is journaled; the Claim stays.
  A missing `events` directory behaves as before. `reopen`, `inspect --timeline`, `search` and
  `close-session` already refused and are unchanged.
- **A provider whose `--version` hangs inside the terminal (#374):** the launch still fails at
  its deadline with `provider launch timed out before startup was confirmed`. New: about two
  seconds later the launch wrapper ends the hung check and exits, where it and the check stayed
  in the terminal until the session was closed. Only the check's direct child is ended; a
  runtime started by a shim script can outlive it. If that check cannot start at all, its text
  is now `failed to start <provider> --version: ...` (it was `failed to query ...`).

## Reorganised, with no behaviour change

- The launch's workspace dialog step is decided in one entry, and each provider adapter supplies
  one policy for the launch (#370). `CONTEXT.md` names the concept: Launch dialog.
- The owner record's two questions, whether it is bound to this Session and whether its macOS
  control fields are complete, have one answer each beside the record's type (#373).
- Completion, failure and cancellation reports pass through one admission step (#368).
- Claude's per-Claim completion records have one owner for their names, shapes and validity
  (#369).
- Resolving the provider executable, reading its version and judging support live in one module
  that the launch preflight, the launch wrapper and `doctor` share (#371).

- Local on the release change: the serial test suite (1788 passed, 0 failed, 6 ignored), Clippy
  with `-D warnings` on the host and for `x86_64-unknown-linux-gnu` and
  `x86_64-pc-windows-msvc`, fmt, the language lint, the scripts tests (109 run, 2 skipped) and
  the integration check.
- CI: each pull request above (#367 to #374) passed all seven jobs on its final head (the Rust
  job on Linux, macOS and Windows, MSRV, both release builds and the integration packages),
  and so did the push of each to main.
- Live, for #367 only, on one Mac with iTerm2 and Claude Code 2.1.322, recorded in
  [the verification record](../verification/2026-11-10-macos-claude-preapproval-dialog-and-version-note.md):
  the first build of that change answered the pre-approval dialog under `--yolo`; the final,
  narrower matcher (exactly two permissions) was checked against the captured screen text, not
  in a new launch. The version note appeared against a state root whose last completed Claude
  session ran 2.1.319, and once more with the final build.
- Not run live: #368 to #374. No provider or terminal was started for them; their evidence is
  the tests. Native Windows ran only on the CI runner, and the new tests of #372 and #374 that
  need a symlink or a stub process run on Unix only. The two-second ordering of #374 between the
  launcher and the wrapper was not raced with real processes.
- No record schema changed. As before, do not downgrade the binary while sessions it opened are
  still open.
