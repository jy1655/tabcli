# Terminal Agent Bridge 0.4.42

0.4.42 ends an `ask` whose launch fails before its Claim is fenced as `failed` instead of
leaving it `launching` (#379), reads the owner record and every core session record under one
policy that refuses links and text that is not UTF-8 (#380, #387), and changes several launch
and terminal error texts (#381, #382, #385, #386). #383 and #384 change nothing a caller can
observe.

## What changes for a caller

- **An `ask` whose launch fails before its Claim is fenced (#379):** a failure between the
  start of the launch and the launcher's fence (host initialization, executable lookup, launch
  command or script install) now ends the session `failed` with the launch error and releases
  its Claim. Before, the session stayed `launching` without a Claim: repair could not settle
  it, no query reported the failure, and `close-session` refused until the launch deadline.
  Since 0.4.41 an iTerm2 or WezTerm `ask` whose request deadline was already spent reached
  that state.
  - With a launch receipt, the request reads `failed` with the error and the session's
    attention includes `launch_failed`. Without one, only the status records the failure and
    the request stays `unresolved`. When the receipt cannot be read, its read error follows
    the launch error in the session's error. The `ask --json` error envelope shows these
    settled values.
  - `close-session` proceeds at once, also when the receipt cannot be read (before, it failed
    with the receipt's read error).
  - When the failure itself cannot be written, the error reads `the failed launch could not
    be settled: <reason>: <launch error>`, the session stays `launching` with its Claim, and
    repair settles it once the deadline of its launch receipt has passed. Without a receipt
    there is no deadline to repair at, and `close-session` is the way out.
  - `reopen` and failures after the fence keep their settlement.
- **Owner record (#380):** every reader of `native-session.json` uses one policy: a link at
  the record's path, anything other than a regular file, a record over 128 KiB and one that is
  not UTF-8 are unreadable.
  - A damaged record (not UTF-8, over 128 KiB, or a link) now blocks `prune` and fails the
    repair and close steps that depend on the owner. Before, such a record was decoded
    lossily, read whole or followed, and its process attested. Doctor reports
    `owner_unreadable` for it. The session stays as it is until the record is repaired or
    removed.
  - A directory at the record's path reads `refusing non-regular session file: <path>`
    instead of the operating system's read error.
  - `origin_observation` reads an owner record of up to 128 KiB; one over 64 KiB was
    `owner_unverified` before.
  - An unbound legacy record and a record of another session are now judged by the liveness
    that dead-owner repair acts on. `inspect` reports `owner.process_alive`, with
    `owner.identity_matches: false` when the process id now belongs to another process, where
    it reported null facts for a record of another session, whose `owner.error` still says so.
    `status` flags `owner_exited` or `owner_identity_mismatch` where it said
    `owner_unverified`. `wait` and `result --wait` end `unresolved` when such an owner is gone
    (a record of another session with an exited process kept the wait going before) and keep
    waiting when an unbound record's recorded birth cannot be inspected. Doctor's evidence for
    an unbound record carries the same facts; its reasons are unchanged.
  - The `tell` prediction in `inspect --json` `capabilities` now follows repair's rule for
    every recorded owner: `owner_ended` when it is attested gone, `owner_unverified` when the
    attestation cannot decide, and `evidence_unreadable` for a record the policy refuses.
    `owner_unattested` remains for a live record of another session or a live unbound one.
    Before, the prediction and repair disagreed for a record of another session with an exited
    process, an unbound record whose process id was reused, a linked record and a record that
    is not UTF-8.
  - Native Windows: only a missing owner record lets `close-session` end a console root that
    never ran on its own; a dangling link or junction now counts as present.
- **Core session records (#387):** the status, the close tombstone, the manifest, the turn
  Claim, the completion journal, the terminal handle and its closing and closed forms, the
  macOS close intent, the hold, the cancel record, the reopen marker and refusal, the provider
  process, the initial prompt and the events are read under the same policy, without a new
  size bound (no reader gained or lost one).
  - A link at the record's path, dangling or not, and any entry that is not a regular file
    are refused (`refusing non-regular session file: <path>`) by every read and every presence
    check. Before, several lifecycle readers followed a link, and presence checks counted a
    dangling link as absent and a link or a directory as present.
  - Text is decoded as strict UTF-8; no reader replaces invalid bytes with U+FFFD any longer.
    A hold or a macOS retained terminal handle with an invalid byte anywhere, in an unknown
    field's value included, is unreadable.
  - `result` for a request whose event is not UTF-8 fails with `failed to read <path>: stream
    did not contain valid UTF-8` instead of reporting `completed` with a repaired answer, and
    attaching that result to a `tell` is refused as unreadable with the same text. `inspect`
    gives that request `bridge_observed_elapsed_reason: unreadable_result`, and doctor's Codex
    terminal diagnosis reports `unavailable` with `failed to read <path>`.
  - A Claim that is not UTF-8 makes the session's snapshot unreadable (`invalid UTF-8: …`)
    instead of yielding a repaired token: `status` lists it as an incomplete reason, and
    `inspect` and `result` fail. `sessions` shows `results: 0` for it, as it already did for a
    linked Claim.
  - A cancel record that is not UTF-8 is reported as an unreadable cancel, and cancel
    admission over a completion journal that is not UTF-8 fails instead of decoding it
    lossily.
  - `search` charges an event's bytes and its read to the scan's budgets before decoding it,
    so an event that is not UTF-8 adds the incomplete reason `<event>: invalid UTF-8: …`
    instead of a hit.
  - `close-session`: a link at `closed.json` is refused on every platform (before, on macOS
    only). A link at `terminal.json`, `terminal.closing.json` or `terminal.closed.json` is
    refused before the terminal adapter runs; before, it was followed, or a dangling one was
    treated as absent. Converging an interrupted close over a dangling link at the journal,
    the Claim or a legacy resume record fails and leaves the link in place, where it used to
    succeed.
  - macOS close: a `terminal.closed.json` that is not UTF-8 carries no consumption reason
    (before, a reason with U+FFFD); the close still finishes. Dead-owner repair over a
    retained `terminal.json` or `terminal.closing.json` that is not UTF-8 fails with `invalid
    retained terminal handle <name>: invalid UTF-8: …` instead of leaving the session as it
    was without an error.
  - Native Windows close: a link, a dangling link or a directory at `terminal.closing.json`
    on a close request is refused; before, it was followed, or the close used `terminal.json`.
  - Error texts for links, directories and invalid text change: an inspection failure other
    than a missing file reads `failed to inspect <path>: …`, and a lifecycle Claim read of
    invalid UTF-8 reads `failed to inspect native turn claim: failed to read <path>: stream did
    not contain valid UTF-8`. Texts for valid, missing and malformed records are unchanged.
  - Pi: the extension reads `turn.claim` and `cancel.json` under the same policy. A refused
    Claim reads as no Claim (no startup record and no cancel), and a refused cancel record as
    no cancel intent. A byte-order mark is kept, as before.
  - `scripts/verify_claude_stop_completion.py` reads `terminal.json` under the same policy and
    reports a refusal as an inspection failure; it still closes the session.
- **Launch host failure text (#386):** when the iTerm2 or WezTerm launch host records a
  failure, the session error names the reason and the stage once:
  `<message> (<reason>); last recorded launch stage: <stage>`. `<message>` is `terminal shell
  environment could not be prepared` for a startup-file failure (`capture_timeout`,
  `capture_exit_nonzero`, `capture_signaled`, `capture_no_output`, `capture_oversized`,
  `capture_invalid`) and `terminal launch host failed` for every other reason, so
  `launch_budget_exhausted` and `capture_spawn_failed` now read `terminal launch host failed`.
  Only `capture_timeout` keeps a detail: `terminal shell environment could not be prepared:
  startup files did not finish within 10000 ms (capture_timeout); last recorded launch stage:
  environment_preparing`. For example, 0.4.41's `terminal launch host failed: binding_mismatch
  at environment_preparing (binding_mismatch); last recorded launch stage:
  environment_preparing` now reads `terminal launch host failed (binding_mismatch); last
  recorded launch stage: environment_preparing`. `doctor`, `inspect --timeline`, the launch log
  and the deadline text are unchanged.
- **Recorded capture budget (#385):** `capture_budget_ms` in `launch-host.json` from the
  `environment_ready` stage on, and in the record of a capture that answered with a failure,
  is the budget the capture enforced, decided when it started, instead of the host's estimate
  made a moment earlier. The two differ only when the launch deadline, not the ten-second
  limit, sets the budget. Then the value, and the `capture_timeout` detail in the session
  error, doctor's `launch_stage` and the timeline that show it, can be a few milliseconds
  lower, for example `within 9996 ms` instead of `within 10000 ms`. The
  `environment_preparing` record and the `shell_environment_started budget_ms=` log line keep
  the estimate. `doctor --probe` reports the budget its `shell_environment` preparation
  enforced, equal to or lower than the earlier estimate, depending on the time that passes
  before the capture starts.
- **Launch admission and a close during the launch (#381):** every check that admits a pending
  launch (the binding waits, the iTerm2/WezTerm launch host, the Ghostty host, the wrapper's
  admission and the spawn fence) now refuses a launch whose close tombstone exists, also while
  `close-session` has written `closed.json` but not yet the status. The wrapper then exits with
  `provider launch cancelled or already attempted; the recorded session is unchanged`, and a
  binding wait ends with its cancelled text. A tombstone or status that cannot be read (a link,
  a directory or malformed JSON) is a read error at those checks, where it was taken as a
  cancelled or no longer eligible launch, or admitted. The spawn fence reports `provider launch
  deadline expired before spawn` before a Claim that belongs to another request or cannot be
  read.
- **Terminal names in shared errors (#382):** shared macOS ownership and shell errors said
  Terminal.app for every terminal. They now name the session's terminal (iTerm2, Terminal.app,
  Ghostty, Warp or WezTerm): `<terminal> ownership requires a live native-session owner`,
  `<terminal> shell no longer owns the native-session process`, `<terminal> shell is attached
  to a different TTY`, `<terminal> shell does not own the expected foreground job` and
  `<terminal> shell identity changed`. Where the terminal is not known, owner registration in
  the wrapper says `terminal shell …`, and the process group check says `terminal process
  group is out of range` or `terminal process group must be positive`. Terminal.app's own
  signal error is unchanged, and so are the close order, the signals and the deadline checks.
- **#383 and #384:** no output, error text, log line, record byte or timing value changes.

## Internal

Round 14 of the architecture review gives each of these facts one owner: the Pending launch
judgment (#381), the owner record observation (#380) and the core record reader (#387), the
stop of an attested owner before its surface ends (#382), launch-host participation in the
terminal registration (#383), the launch host's handoff and the launcher's wait behind the
`Clock` seam, with scripted tests in place of three pseudo-terminal decision tests (#384), the
capture's time budget and one saturating conversion of the receipt deadline (#385), and one
responsibility class per launch host failure reason (#386).

## Verification and upgrade

- Local on the release change (Rust 1.99.1): the serial test suite (1966 passed, 0 failed, 6
  ignored), Clippy with `-D warnings` on the host and for `x86_64-unknown-linux-gnu` and
  `x86_64-pc-windows-msvc`, fmt, the language lint, the scripts tests (112 run, 2 skipped) and
  the integration check.
- CI: the main push of the last merged change (#387, `f4bec8d`) passed all seven jobs: the Rust
  job on Linux, macOS and Windows, MSRV, both release builds and the integration packages.
  Native Windows behavior in this release, including the owner record's never-ran rule and the
  closing-handle refusal, is verified only by that Windows runner.
- No live provider or terminal run was made for this release. The changes are covered by unit
  and integration tests, which use temporary state roots, scripted clocks and, for the owner
  registration errors (#382), real processes on private pseudo-terminals.
- No record schema changed: `launch-host.json` keeps the same bytes (#383), and the other
  changes are in how records are read. A session opened by 0.4.41 is read under the new
  policy after the upgrade. Bridge writes its records as regular UTF-8 files, so the refusals
  above concern records changed by something else.
- A Pi session launched by an earlier release keeps the extension it was launched with, which
  follows a link and replaces invalid UTF-8, until it is relaunched.
- A session that 0.4.41 left `launching` after a launch failure before the fence is not
  settled by the upgrade; `close-session` accepts it once its launch deadline has passed.
- A downgrade below 0.4.42 brings back the earlier readers and is not covered. As before, do
  not downgrade the binary while sessions it opened are still open.
