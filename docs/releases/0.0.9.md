# Agent Bridge 0.0.9

Agent Bridge 0.0.9 adds workspace consent (#28), fixes the Agy follow-up that
lost its receipt (#48), guards the target of a Codex follow-up (#57), explains
a rejected Codex sign-in (#56), reports Agy turn failures at once, and keeps
the keyboard where it was when a session opens (#58). On native Windows a
session now opens as a Windows Terminal tab. This release also repairs native
Windows: 0.0.8 cannot open a session there at all. Windows users of 0.0.8
should update; 0.0.7 is not affected.

## Workspace consent

- Import an exact workspace trust decision from Codex, Claude, Agy, or Pi. Record
  the canonical directory, filesystem identity, owner, and provider-owned source
  in private Bridge state. Parent/child directories and symlink aliases do not
  inherit this record; replacing the directory or changing its owner invalidates it.
- Codex applies an official per-process configuration override. Pi uses its
  official one-run `--approve`. Neither writes a provider trust store or changes
  tool permissions, sandbox policy, or the explicit `--yolo` mapping.
- Claude and Agy have no integrated official process-local trust option. Their
  adapters recognize only the exact startup workspace dialog in a Bridge-owned
  terminal. The terminal compares the captured screen again before one response;
  the adapter then verifies the provider's saved decision. Bridge does not rewrite
  `.claude.json` or Agy settings, so concurrent provider writers remain provider-owned.
  Unknown prompts or changed selections receive no response. Replace these
  fallbacks when the providers expose official trust launch options.
- Claude 2.1.284 displays a Git subdirectory but persists approval at the Git
  root. Its adapter verifies that scope and leaves the native dialog to the user
  when an exact child consent would approve the parent repository. Standalone
  workspaces and exact Git roots remain eligible for the guarded fallback.
- `consent inspect`, `consent revoke`, and `consent reset` expose the record and
  recovery path. Revocation disables Bridge sharing without deleting provider
  trust. A reset permits a fresh import on a subsequent `ask`. If the original
  source is reset or unreadable, Bridge does not silently substitute a target
  that was approved through an earlier shared decision.
- `inspect` and `doctor` report the recorded source and application method.
  Codex and Agy Windows initial console input waits for workspace trust evidence.
  Pi's existing startup receipt remains readiness evidence, not user consent.

## Agy follow-up and workspace trust (#48)

The cause of the missing receipt was found. Agy keeps its workspace-trust
dialog over the composer until the exact workspace is in its own trust store,
and it still runs an initial prompt delivered as a launch argument behind the
dialog. On macOS `ask` therefore returns while the dialog is still open. The
first `tell` was pasted onto the dialog: the text was discarded, its Enter
approved the folder, and Agy logged only its trust reload (356 bytes) and no
receipt. The "deferred skills reload" of earlier notes is this reload; it was
caused by the paste and is not a startup timer.

- A paste now needs two facts: Agy's trust store lists the exact workspace, and
  the session's own `agy.log` shows that this Agy process loaded the workspace
  customizations. The second fact is per process. It is needed because the
  store is shared: a dialog approved in one session leaves the dialog of
  another session of the same workspace open.
- On macOS a follow-up waits for both facts. If they do not hold before the
  request deadline, `tell` fails as `not_sent` before any terminal input, the
  session returns to `ready`, and the error starts with `Agy workspace trust
  was not verified before the deadline` and names the missing fact. A human can
  also approve the dialog while `tell` is waiting.
- Recovery depends on what the managed terminal shows. If it shows the trust
  dialog, approve it there and send the follow-up again. If it shows the
  composer, or the follow-up is still withheld after the approval, close the
  session and start a new one: a log that is missing or has lost the line
  cannot prove that the session trusts the workspace, and the error does not
  claim an open dialog in that case.
- A workspace that another provider already trusts is answered from shared
  consent at `ask`, so its follow-ups need no manual step.
- Behaviour change: in a workspace that no provider has approved, a follow-up
  is now refused until a human approves the dialog. Before, the lost paste
  approved the workspace by accident, and a later attempt then worked.
- The 60-second macOS reload window is removed. After the trust evidence the
  gate needs `CLI startup completed` and one 3.5-second quiet period. In a
  trusted workspace the first follow-up took about 64 seconds before and
  completed in 7.5 seconds on iTerm2 and 6.0 seconds on Terminal.app in the
  live checks of the final source.
- The receipt requirement, the 60-second receipt window, claim retention for an
  unconfirmed paste, and the rule never to paste twice are unchanged. The
  request-scoped `agy-input-<claim>.json` trace is kept.
- `doctor <session>` has a new check `agy_workspace_trust`. It reports
  `available` when both facts hold, `unavailable` with reason
  `agy_workspace_untrusted` when the store does not list the workspace, and
  `unknown` with reason `agy_session_trust_unverified` when the store lists it
  but this session's log does not show the load: either its own dialog is
  still open or the log no longer holds the line. It is an observation; it
  never answers the dialog.
- The Agy dialog matcher used for shared consent now accepts a footer that
  names any model family Agy lists (`Gemini `, `Claude `, `GPT-`). It accepted
  only `Gemini `, which left the dialog unanswered until the `ask` deadline
  when the saved model was a Claude model.
- Native Windows: the initial paste waits for the same two trust facts, and
  this was verified on native Windows with Agy 1.2.10 and 1.2.14. The 45-second
  window is removed. In a workspace that was trusted before the launch, the
  reload it waited for never came. Measured: with the window, the paste came 45
  seconds after startup and `ask` took 53 seconds; without it, the paste came 8
  to 9 seconds after startup and `ask` took 18 to 24 seconds. In an untrusted
  workspace the paste is withheld and `ask` fails as `not_sent` at its
  deadline; the dialog is not touched.

## Agy turn failures are reported at once

When Agy gives up on a turn, for example with `RESOURCE_EXHAUSTED (code 429):
Individual quota reached`, it writes no result. Bridge used to wait for one
until the request timeout.

- The Agy result monitor now records such a turn as a failed request for the
  pending claim, with Agy's own error text, including its reset time when Agy
  gives one. The session returns to `ready`.
- The failure is attributed only when Agy's `agent executor error:` line
  follows the start of the newest turn and the log shows that turn to be the
  pending one: a pasted turn behind the receipt that carries its marker, or the
  first, argument-delivered turn when the only user input in Agy's full
  transcript carries the marker. A turn typed by hand is never attributed.
- A result that Agy has already written is recorded first. Once the failure is
  recorded, a result that arrives later for that turn is not accepted. The
  quota error is the only failure observed so far.
- In the live check with an exhausted model, `ask` failed after 11.0 seconds
  and `tell` after 5.4 seconds instead of running into the timeout.
- Agy offers no way to read the remaining quota without spending a model
  request, so the state cannot be reported before a turn is sent.

## Codex follow-up target (#57)

- Codex `tell` is delivered only through the thread-addressed native queue
  (`codex queue --thread <UUID>`). When the queue prerequisites are unavailable,
  `tell` is refused before any terminal input. There is no terminal fallback,
  because a managed terminal can display another thread or a picker and the
  active thread cannot be verified.
- Codex `tell` requires Codex CLI and a running local app-server daemon at
  0.149.0 or later. Codex 0.147.x and 0.148.x keep `ask` only. Native Windows
  builds up to 0.153.2 have no local daemon lifecycle, so `tell` is unavailable
  there.
- A queue attempt whose outcome is unclear keeps its claim and is never
  repeated through the terminal.
- `doctor` reports `codex_terminal_follow_up=unavailable`.
- In the live check, a queued `tell` completed with the exact result while the
  `/agents` modal was open in the managed TUI, and it left the modal untouched.
  With a queue prerequisite made unavailable, `tell` was refused in under a
  second and the screen was byte-identical before and after.
- Native Windows: Codex CLI 0.159.3 has the local daemon on native Windows.
  With the daemon running, `tell` was delivered through the queue and completed
  in 5.6 seconds. Without it, `tell` was refused in 0.8 seconds before any
  input, and the screen was byte-identical before and after. Bridge does not
  start the daemon. Start it yourself with the command below. On the test PC
  the first start installed a daemon package of 427.5 MB.

  ```text
  codex app-server daemon start
  ```

## Codex MCP authentication diagnostics (#56)

- `MCP client for codex_apps failed to start` with HTTP 401 and `token_revoked`
  means the provider rejected the stored ChatGPT sign-in. In the reported case
  the Codex daemon log showed `refresh_token_invalidated` ("Your session has
  ended. Please log in again."), and the shared daemon and the desktop app
  failed in the same way until the user signed in again.
- A Bridge-launched Codex runs its own in-process app-server and reads the
  stored sign-in at every launch, so each new Bridge session repeats the
  failure until `codex login`. A long-lived Codex process that still fails
  afterwards needs a restart to load the new sign-in.
- `doctor` reports `codex_mcp=unknown`: a completed model turn, the CLI version
  and the daemon state do not prove that MCP started. Its next action explains
  the 401 case and points to `/mcp` in the session, to `codex login`, and to
  the official `codex doctor`.
- Bridge does not read, copy or refresh credentials, does not connect MCP
  servers, does not restart the daemon, and does not resend a prompt.
- The error was not reproduced after the user signed in again, and the session
  in which it was seen was not identified. The issue stays open.
- Native Windows: the Codex logs of the test PC show the same rejection
  (`401`, `token_revoked`) on 2026-09-30, before the sign-in was renewed, and
  none afterwards. A Bridge-launched Codex session after that started its MCP
  clients without an authentication error. Nothing in Bridge differs between
  the platforms here.

## New sessions and the keyboard (#58)

Until now `ask` brought the terminal application to the front and left the new
tab or window selected, so a key typed at that moment went to the managed
session. On 2026-10-01 such keys approved an Agy workspace-trust dialog twice
and broke a launch command once.

- iTerm2 and Terminal.app are no longer activated when a managed session is
  created.
- The tab (iTerm2) or the window (Terminal.app) that had the keyboard is
  selected again right after the new one is created.
- If the user selects another tab or window in the meantime, that choice is
  kept.
- Neither terminal can create a tab or window without selecting it, so the new
  one still has the keyboard for a short time. In the live checks that was 243
  to 450 ms on iTerm2 and 397 to 519 ms on Terminal.app; it is longer under
  load. A key typed in that time still reaches the managed session.
- `ask`, `tell` into the unselected tab or the window behind, and
  `close-session` work as before.
- **NOT-VERIFIED**: whether the terminal application stays behind another
  application on macOS. The macOS live checks ran with the screen locked.
  Ghostty is unchanged. Windows is described in the next section.

## Windows Terminal tabs and the keyboard on Windows (#58)

Until now every session on native Windows opened a console window, and with
Windows Terminal as the default terminal that window came to the front and kept
the keyboard. In the check on the test PC the new window took the foreground
59 ms after it was created.

- A session now opens as a tab of the Windows Terminal window named
  `agent-bridge`. Windows Terminal creates that window for the first session
  and adds a tab for each further one. Closing a session closes its tab; closing
  the last one closes the window.
- A console window of its own is used only when no tab can be had: `wt.exe` is
  not on `PATH`, the desktop has no shell window, a path contains a character
  that Windows Terminal would change, or the tab does not answer within 8
  seconds. `launch.log` in the session directory records the surface and, for a
  console window, the reason.
- The new surface gives the keyboard back to the window that had it. Measured
  with the final source and another application in front: a tab into the
  existing window had the foreground for 109 ms and a console window for 62 ms;
  a first tab, which creates the window, did not take the foreground. Earlier
  builds of the same change measured 94 to 131 ms for a tab and 46 to 47 ms for
  a console window, and a first tab took the foreground in some runs. With a
  Windows Terminal window in front they measured 94 and 115 ms.
- A window you switch to while the session opens gets the keyboard back from
  then on. If you select the new session's window more than 200 ms after the
  keyboard was given back, it keeps the keyboard. Earlier than that, Bridge
  cannot tell your selection from the window's own activation and gives the
  keyboard back.
- Console input typed into the new tab before the session starts is discarded,
  so it cannot answer the provider's first dialog.
- The tab never opens in a window you work in unless you choose that. The
  command below sends it to the most recently used Windows Terminal window;
  `dedicated` restores the default, and without arguments the command prints
  the setting. With `current`, the new tab is selected inside that window and
  stays selected: Windows Terminal cannot create a tab unselected and cannot
  select the earlier tab again.

  ```text
  agent-bridge settings windows-tab-window current
  ```

- The setting is stored in `settings.json` in the Bridge state directory. If
  that file cannot be read, the dedicated window is used and `launch.log` says
  so.
- `launch.log` also records what became of the foreground, for example:

  ```text
  foreground=kept; given back 1 time(s); host window 0x630740
  ```

- Everything about the foreground is best effort and never fails a launch.

## Terminal.app window proof

- A Terminal.app launch could fail with `Agent Bridge could not prove the newly
  created Terminal.app window` and leave the new window open. An earlier window
  whose shell had ended while a close confirmation was pending still reported
  its old tty name, and the new tab had received the same name.
- The launch now considers only windows that did not exist before it, so an
  earlier window is never matched and never returned.
- When the proof still fails, the created window is left open as before. That
  now needs the new window to be missing from Terminal's list, or two new
  windows to report the same tty.

## Repairs for native Windows

- 0.0.8 could not open a session on native Windows. Every `ask` failed in under
  a second with `Windows console launch command contains an unsupported double
  quote`: a line added to the launch command in 0.0.8 used a double-quoted
  string, which the console launch refuses. The published 0.0.8 binary shows the
  failure; 0.0.7 does not have that line. The string is now single-quoted, and a
  Windows test runs the launch command through the launch's own command line.
- A record could not be replaced while another process had it open. Windows
  refuses to rename over an open file, and the launcher reads `launch.json` and
  `status.json` while the session replaces them. In one live run that failed the
  launch with access denied. The rename is now repeated for up to one second on
  access denied and on a sharing violation.
- The screen of a managed console could not be read when it showed full-width
  characters such as Korean text: the read failed with `could not read the
  entire managed console screen`. Shared consent reads the screen before it
  answers a trust dialog, so it could not answer a dialog that showed a Hangul
  path. A row is now accepted with the number of characters the console reports.

not verified, #56 because the reported error was not reproduced, #58 for the
