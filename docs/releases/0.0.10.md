# Agent Bridge 0.0.10

0.0.10 repairs two Codex defects that were found right after 0.0.9 was published
(#60, #61), ends a wait for workspace trust when its session has ended, and adds
three features: a request timeline (#53), the elapsed time that Bridge observed
for a request (#55), and a self-test (#54). Users of Codex should update from
0.0.9. On native Windows 0.0.9 does not send the first prompt in a linked
worktree or a subdirectory of a repository that Codex trusts. On any platform
0.0.9 can record Codex's task title as the result of a short first request.

## Codex initial prompt on native Windows (#60)

On native Windows the first prompt of a Codex session is pasted into the managed
console. A paste that lands on Codex's trust dialog presses its default button
"Trust and continue" with the Enter that follows, so the paste gate withholds
the prompt until there is evidence of trust. In 0.0.9 the evidence was an exact
project entry for the workspace in Codex's configuration, or a consent override
that Bridge applied to the session. Codex CLI 0.159.3 decides more broadly. A
workspace without an exact entry takes the trust of its repository root. That
covers a subdirectory and a linked worktree. Codex shows no trust dialog then
and saves no exact entry. Effect in 0.0.9: the wait for the exact entry never
ended, and `ask` failed at its deadline with the message in the block below while
the terminal showed the composer.

```text
workspace trust is not verified; no initial console input was sent. Approve the exact workspace in the managed provider and start a new request after a timeout
```

Measured with Codex CLI 0.159.3 on the test PC:

| Workspace | `--yolo` | What Codex showed |
| --- | --- | --- |
| A directory that nothing trusts | yes | The trust dialog |
| A directory that nothing trusts | no | The trust dialog |
| A plain directory below a directory with a trusted entry | no | The trust dialog |
| A linked worktree of a repository with an exact trusted entry | no | No dialog; the composer |

- The paste gate now also opens on positive evidence from the screen of the
  managed console: the empty composer row (`› Ask Codex to do anything`). Codex
  draws the composer only when no onboarding screen and no selection view is
  active, so the row means that the trust dialog is over.
- Nothing is inferred from Codex's configuration or from Git. An empty screen, a
  screen that is still loading and a layout Bridge does not know are not
  evidence.
- The screen is read once a second. The path through an exact entry or a consent
  override is unchanged and reads no screen.
- When the user answers the trust dialog in the managed terminal, the composer
  appears and the prompt is sent. In a subdirectory Codex saves the repository
  root and not the workspace, which 0.0.9 never recognised. This case was not
  run live; a test replays the screens.
- Workspace consent that Bridge shares with other providers stays exact.

A wait for workspace trust now ends when its session is `failed`, `exited` or
`closed`. In 0.0.9 the `ask` of a closed session went on waiting until its
deadline. This holds for the Codex wait and for the Agy wait. The session is
looked at before the evidence, so a session that has ended is never pasted into.
The message is in the block below.

```text
the session is closed and no longer waits for workspace trust; no initial console input was sent
```

Live with the repaired build: `ask` in a linked worktree and in a subdirectory
of a trusted repository completed in about 20 seconds each. In a directory that
nothing trusts the dialog stayed untouched, the screen was byte-identical
before and after, and `ask` failed as `not_sent` at its deadline. Closing a
waiting session ended its `ask` in 0.5 seconds. The first version of the repair
inferred the missing dialog from `git rev-parse` and used the screen only to
look for the dialog's words. A review found that an empty screen passed that
check and that the inference differed from Codex's own rule. That version was
not released.

## Codex task title turn (#61)

Bridge learns that a Codex turn has finished from Codex's `notify` hook. It
appends a turn marker to the prompt and, in 0.0.9, accepted a notification whose
input ends with the marker. Codex CLI 0.159.3 answers the first message of a TUI
with a second turn, on a thread of its own: the task title turn. That turn sends
its own notification. Its input is Codex's instruction followed by the user's
whole message, so it ends with the marker too. Whichever notification arrived
first became the result of the first request. On the test PC the same short
prompt gave `{"title":"READY"}` as the result in two of six runs, and the thread
of the task title turn was recorded as the session's thread, which a later
`tell` would address. Long prompts were not affected in the runs of this work.
The title input appears to cut the message; the length at which that happens was
not measured.

- The input of a notification is accepted only when it begins with the header
  that Bridge puts in front of every prompt (`[Agent Bridge native delegation]`)
  and ends with the turn marker. A turn that Codex starts itself quotes the
  message behind its own instruction and does not begin with the header.
- With `/ide` on, the Codex TUI puts its IDE context in front of the message: a
  first line `# Context from my IDE setup:`, the context, and a line
  `## My request for Codex:`. That input is accepted as well. The wrapper is
  taken from Codex's source (rust-v0.159.3) and was not observed live.
- The header tells Bridge's framing from that of a turn Codex starts. It is not
  an identity of the turn; Codex gives none before the first notification.

Live with the repaired build: six of six short first requests returned the
answer. With the release candidate, three of three short first requests in a
linked worktree returned the answer, and the self-test completed both of its
requests with Codex while a local Codex daemon was running. Not run: macOS, and
a session with `/ide` on.

## Request timeline (#53)

`inspect` gains a view that puts the preserved records of a session in the order
of the times they carry.

```text
agent-bridge inspect <session> --timeline [--request REQUEST] [--json]
```

- Per request it shows the request receipt, the published completion event, and
  for the initial request the launch phase.
- Per session, without a request to attribute them to, it shows the lines of
  `launch.log`, the status and close records, the terminal close records, the
  request and event indexes, and legacy events.
- Every entry names its session, its request and event when it belongs to one,
  a stage, the observed time or unknown, the source record, and the state of
  that record: `observed`, `missing`, `unreadable` or `unpublished`.
- Each request also carries its state as the request-scoped `result` reports it
  at the time of the query (`completed`, `failed`, `pending`, `unresolved`,
  `recovery_required`, `unknown`), whether a completion is recorded, the elapsed
  time of section "Elapsed time", and the exact `result` command.
- Nothing is inferred in the entries. A launch deadline is not shown as the time
  of a phase. A receipt time is the creation of the receipt and not a delivery.
  A `launch.log` line is shown with its timestamp and its text only.
- A record that changes while the query reads is reported as a failed query, not
  as a timeline.
- The query repairs nothing, resends nothing, closes nothing and writes nothing.
  The default `inspect` output and `result` are unchanged.
- `--request` needs `--timeline`. It filters the request entries and keeps the
  session entries.
- Every record is read once for one timeline and must be valid UTF-8. A record
  that is not is reported as `unreadable` with the reason.
- `launch.log` is read up to 1 MiB and every other record up to 64 MiB. A larger
  log is reported as an `unreadable` entry with its size and the limit, and the
  timeline is marked `incomplete`.
- A `launch.log` line whose leading number is not a usable time is shown with an
  unknown time.
- Each request summary carries `derived_from` with the value `result`. Its state
  and its diagnostic are what the request-scoped `result` reports at the time of
  the query, including the diagnostic for a launch whose recorded deadline has
  passed. The launch entry shows only what `launch.json` holds.

## Elapsed time (#55)

Results now say how long Bridge observed a request to take.

- `bridge_observed_elapsed_ms` is the number of milliseconds from the creation
  of the request receipt to the creation time of the published completion event,
  or `null`.
- `bridge_observed_elapsed_reason` is `null` when the value is computed.
  Otherwise it is one of: `no_published_result`, `missing_receipt` (a legacy
  event without a receipt), `missing_receipt_time`, `missing_result_time`,
  `inverted_time`, and in `inspect` `unreadable_result`.
- The two fields are in the request-scoped `result`, in every entry of
  `result --list`, in `inspect` (the latest result and every request), in the
  timeline, and in a finished `ask` or `tell` response.
- The human output of `result` prints `Bridge observed elapsed: N ms` or the
  reason.
- The value is wall-clock time that Bridge observed, including dispatch and
  delivery. It is not model time and not billing time. A result time earlier
  than the receipt time is reported as `inverted_time` and not corrected to
  zero. Equal times give `0`.
- The value is computed on every query and is not stored.
- To report a record without a time, `created_unix_ms` of a receipt and of an
  event is optional when a record is read. Every writer still writes it,
  attaching a result as context still requires it, and a completion that lacks
  it is not published.
- No provider usage (tokens, cost) is collected. The signals Bridge receives
  today carry none: the Codex notify payload, the Claude `Stop` hook input, the
  Pi lifecycle events as the extension reads them, and the Agy transcript. That
  says nothing about usage APIs the providers may have.

## Self-test (#54)

A command that checks a real round trip with an installed provider.

```text
agent-bridge self-test <codex|claude|agy|pi> [--workspace PATH]
    [--terminal <ghostty|iterm2|terminal|windows-console>]
    [--model MODEL] [--effort EFFORT] [--yolo]
    [--timeout-secs N] [--isolated] [--json]
```

- It makes real model calls and opens a real terminal. Nothing else calls it.
- It runs five steps through the public commands: `ask`, `initial_result`,
  `tell`, `follow_up_result`, `cleanup`. Both requests must return the run's
  unique marker, each under a request and an event of its own.
- Each step ends as `passed`, `failed`, `timed_out`, `unsupported` or
  `not_verified`. The report gives per step the elapsed time, the request and
  event address and the reason, and for the run the Bridge version, the
  provider version, the terminal, the state root, the session and its state
  after cleanup.
- The exit code is 0 only when every step and the cleanup passed.
- By default it runs in the ordinary state root, with its settings and consent
  records. The session it closes is the one whose id its own `ask` reported.
  Only when `ask` reported none does it look for the session by the unique
  title of the run, and it accepts exactly one match.
- With `--isolated` the run uses a private state directory of its own, below
  `AGENT_BRIDGE_NATIVE_STATE_DIR` when that is set and below the system
  temporary directory otherwise. The settings and the consent records of the
  ordinary state root do not apply to it, and the directory stays until the user
  removes it.
- It never resends a prompt whose delivery is uncertain, never approves
  workspace trust, never prunes, and never closes a session it did not create.
  Closed sessions stay in the state root like every closed session.
- `--timeout-secs` is a budget per command, 120 seconds by default, not a limit
  for the whole run.
- A request command has its `--timeout-secs` budget plus 5 seconds; each close
  and each confirmation has 10 seconds. A command that does not return within
  its bound is ended and its step is reported as `timed_out`. The cleanup is
  still attempted.
- With `--isolated` every session of the private directory is closed, the one
  that `ask` reported first, and the report lists each of them in
  `cleanup_sessions`.

Live on the test PC with the release candidate (Windows Terminal 1.24):

| Provider | Mode | Result |
| --- | --- | --- |
| Claude Code 2.1.287 | default | Every step passed in 43.3 s (`session-5aU43A`) |
| Claude Code 2.1.287 | `--isolated` | Every step passed in 37.7 s (`session-O71WMr`) |
| Agy 1.2.14 | default | Every step passed in 58.8 s (`session-xFslsi`) |
| Pi 0.99.2 | default | Every step passed in 11.0 s (`session-Zo5WLc`) |
| Codex CLI 0.159.3, local daemon running | default | Every step passed in 25.7 s (`session-TXv9Kk`) |
| Codex CLI 0.159.3, no local daemon | default | `tell` ended as `unsupported` and the run exited with code 1 after 21.4 s; the session was closed (`session-VJ9pza`) |

Every run used a state root given through `AGENT_BRIDGE_NATIVE_STATE_DIR`, and a
Codex `tell` needs a running local Codex daemon, which Bridge does not start.

## Pi on native Windows

The Pi sign-in on the test PC was renewed, so the Pi checks that 0.0.9 left open
were run with Pi 0.99.2 and the 0.0.9 code. No `--yolo` was used.

| Case | Evidence | Result |
| --- | --- | --- |
| Workspace that Codex trusts exactly | `session-TUTYoG` | Consent `verified`, `applied=pi-approve-once`; `ask` 8.8 s, `tell` 2.6 s |
| Workspace that Agy trusts exactly, with project resources under `.pi` | `session-3W1uzJ` | Consent `verified`, `applied=pi-approve-once`; no trust dialog; `ask` 7.9 s, `tell` 1.9 s; Pi's trust store not created |
| Workspace that nothing trusts, without project resources | `session-aBKIBB` | Pi showed no dialog; `ask` completed; nothing applied |
| Workspace that nothing trusts, with project resources under `.pi` | `session-bX0oI0` | Pi showed `Trust project folder?`; the initial input was withheld; `ask` failed at its 45 s deadline; screen byte-identical; Pi's trust store not created |

Pi workspace consent, Pi `tell` and the Pi input gate are thereby verified on
native Windows; Claude workspace consent on native Windows is still not
verified.

## Verification boundary

The evidence is in
[`docs/verification/2026-10-02-windows.md`](../verification/2026-10-02-windows.md).

The two Codex repairs were reviewed by Codex through Agent Bridge, and both were
reworked after the review. The three features were implemented by Codex sessions
through Agent Bridge and reviewed in a separate Codex session; that review found
eight defects. Seven were repaired, each with a test that failed before the
repair, and one was answered by the `derived_from` field of the timeline. No
review ran after those repairs.

Not verified:

- macOS. Every change of this release was run on native Windows only. The macOS
  and Linux targets were compiled and linted.
- A Codex session with `/ide` on.
- A user who answers the Codex trust dialog while `ask` waits.
- The length at which Codex's task title input cuts a prompt.
- Claude workspace consent on native Windows.
- Provider usage of any kind.
- Everything that the 0.0.9 notes list as not verified on native Windows, except
  Pi.

Issues #53, #54 and #55 are implemented in this release; the second stage of #55
(provider usage) is open. Issues #60 and #61 are repaired in this release.
