# Terminal Agent Bridge 0.2.3

0.2.3 keeps the record of a Warp launch that fails after its tab exists, reports whether Pi has
credentials configured for a session's provider, and explains the Codex startup line about the
shared background server. Commands, output, session records and provider transports are those
of 0.2.2, and there is nothing to migrate. A session launched by 0.2.2 is read as it is.

## Fixes

- A Warp tab launch that proved its tab and then failed to write the control binding returned
  a text error when the exact cleanup also failed, so the session was recorded closed without
  the tab it may still have (#87). The adapter now returns the proven handle as data, as the
  Ghostty adapter does since #86: the launcher keeps it in `terminal.json`, marks the session
  `failed` with the surface named and the residual-surface warning in `status.error`, and the
  two orderings fenced in 0.2.2 hold for Warp. A confirmed cleanup still records a plain
  failure without a handle. A later `close-session --explicit` does not close that tab: the
  Warp close needs the control binding that failed to persist, so the close refuses and keeps
  the handle, and the tab is closed by hand. The recovery close stays open in #87.

## Diagnostics

- Pi refuses a prompt for a missing provider login before any extension event fires, so a
  request to such a session stays pending until the caller's timeout and the caller sees a
  timeout, not the refusal (#83). Pi gives no signal that identifies the refused request, so
  nothing is recorded as failed. `doctor <session> --probe` now reports
  `pi_provider_credentials` from Pi's own `auth check --no-refresh`, without a model call or
  credential output: `ready` means configured, not accepted; `not_ready` means Pi reports no
  configured credentials; a missing command, a timeout, an unqualified model name or an
  unreadable answer is `unknown`. `doctor --provider pi` has no model and reports `unknown`.
  A timed-out `self-test pi` result step includes the same observation in its reason. The
  request stays pending and claimed, nothing is resent and no prompt is answered.

## Documentation

- The [providers page](../providers.md) says that a Bridge-launched Codex TUI runs on its
  embedded app server because Bridge passes its `notify` hook and the verified workspace
  trust as process-local overrides, that the startup line `Running without the shared
  background server: command-line configuration overrides ... requires embedded mode.` is
  expected when Codex's daemon auto-start is enabled, and that the `/agents` dialog offering
  to start a background server is not answered by Bridge (#89).
- The command reference, the terminals page, the providers page and the testing guide describe
  the retained Warp handle, the Pi credential check and the self-test reason.

## Verification and remaining limits

- macOS tests passed: 734 tests, no failures, 6 ignored (five live tests and one
  subprocess fixture). Clippy passed for the host, `x86_64-unknown-linux-gnu` and
  `x86_64-pc-windows-msvc`; formatting and diff checks passed. Ignored tests are not runtime
  evidence.
- Linux and native Windows were checked locally, not run. Their tests run in CI and in the
  Release workflow for the tagged commit.
- The Warp fix is covered by fake-runner tests of the retained and the confirmed cleanup, the
  close during creation and the late handoff, each of which fails against the old code. No
  Warp session was launched: Warp support is not live-verified (#63), and the record write
  that fails here has not been seen to fail live.
- The Pi check was exercised live: `self-test pi` in WezTerm with `--model openai/gpt-4o-mini`,
  for which this machine's Pi has no credentials, timed out at the initial result after 120 s
  and reported `Pi provider credentials not_ready for openai` in the step reason, and
  `doctor <session> --probe` on a separate `ask` to the same model reported
  `pi_provider_credentials` as `not_ready` with exit code 1. Nothing was resent and both
  sessions were closed. Pi's own refusal screen was not read.
- Authenticated macOS round trips through `self-test` with provider defaults (ask, result,
  `tell`, result, owned-session cleanup), with the screen unlocked: Codex 0.160.1 in iTerm2;
  Pi 1.0.0 in WezTerm with `--model openai-codex/gpt-5.6-sol`; Claude Code 2.1.292 in WezTerm;
  Agy 1.3.0 in WezTerm in its default permission mode. Ghostty and Terminal.app were not
  repeated: their Codex rows passed for 0.2.2 on the same day and no terminal adapter other
  than Warp changed.
- Not exercised with this release: native Windows and Linux at runtime, Warp, a close after
  the owner died, provider approval prompts, and a Codex `tell` while a shared daemon is
  known to be absent.
- The limits recorded for 0.1.1, 0.1.2, 0.2.0, 0.2.1 and 0.2.2 are unchanged.
